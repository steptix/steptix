# Asking the model for a value: `[use ai]`

Status: built 2026-09-24. The live test (`use-ai.test.cjs`) passed on its
first run. Known issue: [060](../issues/060-use-ai-step-stores-a-masked-secret-and-passes.md),
where a step that needs a secret stores `***` and passes.

## In plain terms

Every step today is about something outside the test. A page step reads or
drives the browser, a `[use computer]` step drives the desktop, a `[tool:]`
step runs the author's code, and `Set` copies text between variables. There
is no way to say *"make up a value for me"*: a customer name, a paragraph of
filler text, a date three days after one you already have. Written as an
ordinary step, the sentence goes to the page model, whose only way to store
anything is to read it off the page. The best case is a refusal. The worst
case is a green step that stored some date that happened to be on screen.

This story adds one step form:

```markdown
5. [use ai] Create a name starting with "AUTO" and ending with a random 4 digit number and store it in random_name
```

The step's text, with its placeholders filled in, goes to the model on its
own: no page, no DOM, no screenshot, no earlier steps, no date. The model
replies with the value, and the framework stores it under the name the step
asked for. Later steps use it as `{{random_name}}` like any captured value.

Three rules make it what it is:

- **The model answers on every run.** It is never cached and never compiled
  into code-behind. Whether a value should be the same every time is the
  author's decision, and an author who wants that writes a `[tool:]`.
- **The step text is everything the model knows.** The framework adds no
  date, no time and no context. If "today" matters, the author puts today in
  the step, from a variable or as a literal.
- **Nothing conversational is ever stored.** The model answers in a fixed
  JSON shape, the value field holds only the value, and an empty answer or a
  refusal fails the step with the model's reason rather than storing `""`.

The author names the value in their own words ("store it in random_name").
When they want the name guaranteed, `[store as: random_name]` pins it and
the framework uses that name whatever the model says.

### What it looks like in practice

**You write:**
`[use ai] Create a name starting with "AUTO" and ending with a random 4 digit number and store it in random_name`
**You get:** `{{random_name}}` = `AUTO4821`. The report's ◆ Captured box
shows the value, the TestBench Variables panel lists it as *generated by the
model*, and the run's token count includes one small model call. Run it
again and the model is asked again. Models are poor random-number
generators, so the same number may well come back; the author knows that.

**You write:**
`[use ai] Today is {{today}}. Give the date 3 days later as yyyymmdd [store as: days_from_now]`
**You get:** `{{days_from_now}}` = `20260927` when `{{today}}` holds
`2026-09-24`. The name comes from the `[store as:]`, not from the model.

**You write:**
`[use ai] Give the date 3 days from today as yyyymmdd and store it in days_from_now`
**You get:** most likely a failed step. The model is told not to guess, so it
should reply with an error ("the step asks for a date relative to today but
does not say what today is"), and the report shows that reason. If the model
guesses anyway, the step passes with the guess. The framework cannot tell a
guess from an answer, which is why the docs say to put the date in the step.

**You write:** `[use ai] Write a random paragraph of text about Australia`
**You get:** it depends on the name the model picks, because the step never
gives one. An invented name such as `australia_paragraph` fails the step:
it is not in the step, so no later step can be relying on it, and the error
names the model's choice and the two fixes (say it in the step, "…and store
it in text", or add `[store as: text]`). But a word lifted from the
sentence, such as `paragraph`, passes the check and is stored, and a later
`{{text}}` is then left literal with only a warning. The check rules out
invented names, not unnamed steps. So always name the value. (Measured
while building: a scripted reply of `"as": "paragraph"` stored
`{{paragraph}}`. The user chose to keep this loose check over a stricter
grammar, 2026-09-24. Against the real model the same step failed anyway:
it replied `{"error": "No variable name was specified."}`. That is the
model following the prompt, though, not a guarantee.)

**You write:** `Write a random paragraph about Australia [use ai] [store as: text]`
**You get:** a parse error before any browser opens: `[use ai]` goes at the
start of the step.

**You compile** a test containing any of the steps above.
**You get:** every other step compiled as usual, and the `[use ai]` steps
listed as *not compiled: a [use ai] step asks the model on every run*. A
compiled replay of that test still makes one model call per `[use ai]` step.

## Verification rule for this story

"Done" means all of the following, each proven by a test named in §Tests:

1. A `[use ai]` step sends the model exactly one system message and one user
   message, and the user message contains the step text with placeholders
   filled in and **nothing else from the test**: no DOM, no screenshot, no
   `## Values` block, no conversation history, no date.
2. It never reads or writes the step cache, is never offered for compile by
   any of the three compile classifiers, is never written as an `ai: true`
   entry, and a hand-written `.steps.ts` entry for its text is never run.
   Running the same test twice makes a model call for the step both times.
3. A reply of `{"as": n, "value": v}` stores `v` under the step's name. With
   an explicit name (`[store as: x]`, `[as: x]`, `[output: x]`,
   `store as {{x}}`) the name is `x` whatever `as` says. With no explicit
   name, `n` is used only if it appears in the step text as a whole word
   (case-insensitive); otherwise the step fails, naming `n` and the two fixes.
4. `{"error": r}` fails the step with `r` in the error and is **not**
   retried. A reply that is not one of the two shapes, has an empty value
   after trimming, or has a value that is an object or an array fails the
   step and is retried within `execution.retries`, the retry prompt saying
   what was wrong.
5. A `{{name}}` or `${…}` in the step that the run cannot resolve fails the
   step before any model call, naming the reference, in the words `Set` uses.
6. A secret-named value that fills a placeholder reaches the model as `***`,
   by the same membership rule the page model's `## Values` block uses
   (`## Config: unmask:` exempts a name). A value stored under a secret-named
   variable is masked everywhere a `Set` value is.
7. It works in all four step loops (CLI, including hooks; Sessions API;
   errand; Electron adapter), in computer mode without taking the computer
   lock, inside `### Section` bodies, loops and data-row runs, and inside a
   skill body when the name is explicit.
8. The value is visible everywhere a `Set` value is: the CLI step line, the
   report's ◆ Captured box, the `capture` stream event (with a new
   `source: 'generated'`), `session.outputs`, the errand receipt's
   `captures`, and the TestBench Variables panel.
9. `[use ai] <text>` is accepted, and every misuse below is refused with its
   own message, by the markdown parser, the MCP assembler and the TestBench
   diagnostics, with the runtime and runner-core copies of the grammar held
   together by the existing parity test.

## Context: what exists, and what is missing

**`[use` is already claimed, and `[use ai]` is refused today.** Computer
mode added `[use computer]` and `[use browser]` as whole-step mode switches
(docs/specs/SPEC-use-computer.md §4.1). The claim regex in
`src/parser/use-step.ts` (`CLAIM_RE`) matches any line opening `[use`, and
`useStepError` refuses `[use ai] …` as "`ai` is not a surface this framework
drives". That refusal fires in the markdown parser (`markdown.ts`, the
authored-step check and the control-line-tail check), in the MCP assembler
(`src/mcp/assemble.ts`) and, through the runner-core mirror
(`runner-core/src/use-step.ts`), as a TestBench squiggle. On paths with no
validator (Sessions API POSTs, hook lines, errands), `parseUseStep` returns
`null` and the line goes to the page model as prose. So this story extends
an existing grammar rather than adding a bracket. SPEC-use-computer §3 and
§12 already name a per-step `[use computer] Click Save` as a deferred
addition; `[use ai] <text>` is the first per-step member of the family. It
is the only one that has no mode form: `ai` is not a surface.

**`Set` is the template.** It is the one existing step that writes a
variable with no page, and it is dispatched the same way in all four loops:
`parseSetStep` on the authored line before interpolation, then one shared
runner (`src/runner/set-step-runner.ts`, `runSetStep`) that resolves the
template with `resolveSetTemplate`, writes with `bindVariable`, and returns
a `StepResult` with `turns: []` and `outputs: { [name]: value }`. Each loop
then does its own bookkeeping:

- the CLI prints a masked `[set] …` line;
- the server writes `session.outputs` and `outputSources` and emits
  `capture` with `source: 'assignment'`;
- the errand writes `captures`;
- the Electron adapter emits nothing, because it has no variables event.

Because `Set` is dispatched before `executeStep`, it never touches the step
cache (the only reader and writer is `executeStep`, gated by
`cacheEnabledFor`) and never runs code-behind. `[use ai]` inherits both for
free by being dispatched at the same place.

**`[store as: x]` is only a hint today.** No parser turns it into a
variable. It stays in the text sent to the page model, rule 13 of the system
prompt (`src/ai/prompts.ts`) tells the model to use that name exactly, and
the value is bound when the model's `read` action carries `as`. For
`[use ai]` the framework reads the name itself, which is a stronger promise
than page steps make.

**No model call today sends no page.** The closest precedents are the grid
structure question (`buildGridStructurePrompt` / `parseGridStructureAnswer`,
its own short system prompt and parser) and `diagnoseFailure`. `AiClient`
already forces `responseFormat: { type: 'json_object' }` on every call and
throws on an empty reply, so a JSON answer is what the client wants anyway.
`extractJson` (`src/ai/action-parser.ts`) strips fences and takes the first
balanced value.

**Filling placeholders does not mask secrets.** `interpolate` and
`resolveSetTemplate` insert real values. The page model never sees them
because it gets the step with `{{…}}` left in plus a `## Values` block built
by `maskValueForPrompt`. `[use ai]` sends filled-in text, so it has to mask
by itself with `redact(text, runSecrets(…))`.

**There is no built-in date or random value.** The handbook says so (§4.1,
"No implicit variables"). This story does not add one; the author supplies
the date, or writes a tool.

## Decisions

1. **Never cached, never compiled.** The user's rule, and the reason the
   step exists as something other than a tool. The dispatch point enforces
   the cache half. All three compile classifiers get an explicit
   ineligible reason, *"a [use ai] step asks the model on every run"*:
   `describeSteps` (`src/codebehind/compile.ts`), `generationRefusal`
   (`src/codebehind/live-compile.ts`) and `refuseReason`
   (`src/codebehind/generate.ts`). The live-compile check matters on its own
   terms: `generationRefusal` has no `Set` check today, and the mapping
   suggests (unproven) that a `Set` step falls through to "the recorded run
   performed no page actions" and is written as an `ai: true` entry. A
   `[use ai]` step must not repeat that. The implementer should confirm the
   `Set` behaviour and, if it is real, fix it in the same place, since it is
   the same missing check.

2. **The step text is the whole context.** The user message is the resolved
   step text and nothing more. The framework adds no date, time, timezone,
   test name, context notes or earlier steps. The author supplies what the
   model needs.

3. **Prefix only: `[use ai]` opens the step.** After an optional
   `[no-hooks]`, stripped by the parser itself as `use-step.ts` already does
   for the reason given there (runner-core keeps the marker on the wire).
   Case-insensitive, whitespace-tolerant, colon optional (`[use: ai]`), as
   the rest of the family. A `[use ai]` anywhere else in the line is a parse
   error that says to move it to the start: the bracket is unambiguous
   intent, and left alone it would reach the page model as prose.

4. **Placeholders are filled, then secrets masked, then sent.** Every
   `{{name}}` and `${…}` is resolved in one pass with the resolver `Set`
   uses. An unresolved reference fails the step before any model call. An
   ordinary step passes an unresolved placeholder to the model with a
   warning, but here a literal `{{today}}` would invite the model to invent
   a date, which is the silent wrong value this codebase treats as the
   worst failure. Names the step *defines* (`store as {{x}}`) are
   definitions, not references, and are excluded the way
   `inlineStoreAsNames` already excludes them. Secret-named values are then
   replaced with `***` using the run's secret set, honouring
   `## Config: unmask:`. A step cannot compute from a secret; that is the
   right trade.

5. **The reply shape.** The model replies with JSON only, one of:

   ```json
   { "as": "random_name", "value": "AUTO4821" }
   { "error": "The step asks for a date relative to today but does not say what today is." }
   ```

   - `value` is a string. A number or boolean is accepted and stored as its
     string form (`42` → `"42"`, as `count` stores). An object or array is
     refused: lists are not in this story. Leading and trailing whitespace
     is trimmed; an empty result fails the step.
   - `error` is a real outcome, not a formatting failure. It fails the step
     with the model's reason in the error and is **not retried**: asking
     again until the model stops refusing is how a guess gets stored.
   - Both keys, neither key, invalid JSON, or an empty or non-string value
     fail the attempt with a named reason and are retried within
     `execution.retries`, the retry prompt carrying the reason. These are
     transient formatting failures, the kind retries exist for.

6. **The name: explicit if written, else the model's, checked.** An explicit
   name is one of `[store as: x]`, `[as: x]`, `[output: x]`, or the prose
   `store as {{x}}` / `save as {{x}}`. Exactly one explicit name is
   authoritative: the framework binds `x` and ignores the model's `as`. The
   bracket markers are stripped from the text the model sees, since they
   are instructions to the framework; the prose form stays, since it is part
   of the author's sentence. More than one distinct explicit name is
   refused, at parse time where the file is parsed and at run time on the
   paths that do not parse: a `[use ai]` step produces one value.

   With no explicit name the model's `as` is used if it is a `\w+` name that
   appears in the step text as a whole word, case-insensitive. Otherwise
   the step fails: *"the model named the value `australia_paragraph`, which
   the step does not mention; say what to call it in the step, or add
   `[store as: name]`"*. This is retried like any formatting failure, since
   a model that misspelled a name the step does give will usually correct
   it when told. The check exists because an unbound plain `{{name}}` in a
   later step is left literal with only a warning
   (`placeholder-substitution.ts`, the dotted-only refusal), so a name the
   author did not expect would fail silently three steps later.

   **What the check does not catch**, found while building: a step that
   never names its value at all. Any word of the sentence passes, so
   `Write a random paragraph of text about Australia` is stored as
   `{{paragraph}}` if that is what the model answers. Tighter rules were
   offered: the framework reading a naming phrase ("store it in X") itself,
   or the name having to follow a naming word. The user kept the loose
   check on 2026-09-24. The docs therefore tell authors to always name the
   value, and describe the check as ruling out invented names only.

7. **Inside a skill body the name must be explicit.** A skill's scoping
   (internal names become `__skill<N>_…`, declared outputs are aliased)
   works by rewriting names in the step text at expansion (`renameVar`,
   `referencedVariableNames().captures`). A name the model makes up at run
   time never passes through that rewrite, so it would land in the caller's
   scope unrenamed. A `[use ai]` step in a skill body with no explicit name
   is refused when the skill is parsed, with a message that says why and
   shows `[store as: …]`. `### Section` bodies share the test's scope and
   need no such rule.

8. **Dispatched where `Set` is, in all four loops.** One shared runner, one
   branch per loop, on the authored text, before interpolation, beside the
   `Set` branch. It inherits `Set`'s exemptions: the conditional grouper
   (`step-grouper.ts`) must not swallow it as an `If` step's continuation,
   and `stepReadsScreen` (`computer-step.ts`) must say no, so it takes no
   computer lock. Errands currently refuse `[use …]` at run time as a
   surface switch; `[use ai]` is not a surface switch and is allowed there.
   A `[use ai]` step as the tail of a control line (`If … then [use ai] …`)
   stays refused in this story, with a message saying so.

9. **A new capture source, `'generated'`.** `CaptureEvent.source`
   (`runner-core/src/protocol.ts`) becomes
   `'capture' | 'toolOutput' | 'assignment' | 'generated'`. The Variables
   panel labels it *generated by the model*. Old clients collapse unknown
   sources to `'capture'` by the rule on the type. This is a runner-core
   change and therefore a `testbench-native` patch bump.

10. **Failure tails apply as on any step.** `otherwise continue with
    warning …` and `otherwise fail … with message …`
    (stories/step-failure-outcomes.md) are stripped before the text goes to
    the model and applied by the framework to the step's outcome.

11. **Keyless and model routing need nothing new.** The step goes through
    `AiClient.complete` with the run's model, so a machine with no key fails
    it with the existing `AiNotConfiguredError` message, and routing and
    token accounting are the ones every step uses. The call is recorded as
    an `AiInteraction` with a new `purpose: 'use-ai'`.

## Design

### Parser: `src/parser/use-step.ts` (extended) and its runner-core mirror

`parseUseAiStep(raw)` returns `{ text, explicitNames }` or `null`:

- `text` is the step after `[use ai]`, with bracket name markers removed;
- `explicitNames` holds the distinct names from `[store as:]`, `[as:]`,
  `[output:]` and prose `store as {{x}}`.

`useStepError(raw)` learns the new member and its refusals:

- `[use ai]` alone: "`[use ai]` needs a step after it: what should the model
  produce?"
- `[use ai timeout=30] …`, i.e. arguments inside the bracket: refused as for
  the other two.
- `[use ai]` not at the start of the step: "put `[use ai]` at the start of
  the step".
- More than one explicit name: refused, naming them.
- `[use phone]`, unknown target: the message now describes the family as
  it is, with `[use computer]` / `[use browser]` switching mode as whole
  steps and `[use ai] <step>` asking the model for a value.
- `[use computer] and click Save` keeps its whole-step refusal, since the
  per-step surface prefix is still deferred.

`parseUseStep` keeps returning `null` for `[use ai] …`, so no existing
caller changes meaning. The skill-body rule (decision 7) is a separate
check where skill bodies are validated, because only that layer knows the
line is in a skill.

The runner-core copy (`runner-core/src/use-step.ts`) changes in step, and
`tests/use-step-parity.test.ts` gains the new lines. The refusal-list tests
(`tests/use-step.test.ts`, `runner-core/tests/use-step.test.js`) are updated,
not deleted. `whole-step-bracket.ts`'s directive lists and message are
brought into line in both copies.

### Shared runner: `src/runner/use-ai-step-runner.ts` (new)

`runUseAiStep({ parsed, index, instruction, scope, envData, secrets,
aiClient, retries, signal })` returns `{ result, name?, value? }`:

1. Resolve the text (decision 4). An unresolved reference returns the
   failed `StepResult` shape `runSetStep` uses, with no model call.
2. Mask secrets in the resolved text.
3. Build the messages with `buildUseAiPrompt(text, explicitName?)`, a new
   export in `src/ai/prompts.ts`. The system prompt:

   > You produce the value of one variable in an automated test. There is
   > no web page, no screen and no earlier conversation: the step below is
   > everything you know.
   >
   > Reply with a JSON object and nothing else, in one of two shapes:
   > `{"as": "<variable name>", "value": "<the value>"}` or
   > `{"error": "<why the step cannot be done as written>"}`.
   >
   > "value" is stored exactly as you write it and used by later steps. Put
   > only the requested content in it: no preamble, no explanation, no
   > surrounding quotes, and no Markdown unless the step asks for it.
   >
   > "as" is the variable name the step asks for, spelled as the step
   > spells it.
   >
   > If the step cannot be done from its own words (for example, it needs
   > today's date and does not give it), reply with "error" and say what is
   > missing. Do not guess to fill the gap.

   With an explicit name, the "as" paragraph is replaced by "The framework
   already knows the variable's name; omit "as"." The user message is the
   masked text and nothing else.
4. Call `aiClient.complete` and parse with `parseUseAiReply` (new, in
   `src/ai/action-parser.ts`, on top of `extractJson`), which returns
   `{ kind: 'value', as?, value } | { kind: 'error', reason } |
   { kind: 'malformed', why }`.
5. Apply decisions 5 and 6. On success, `bindVariable(scope, name, value)`
   and return a passed `StepResult` with one turn holding the model call and
   no actions (the `guardResult` shape in `control-runtime.ts`), `outputs:
   { [name]: value }` (left out for `__skill*` names, as `runSetStep` does),
   and `aiExplanation: '[use ai] <name> = "<value>"'`.

The runner does not mask its own result. Masking of outputs is the loops'
existing job, exactly as for `Set`.

### The four loops

Each gains one branch beside its `Set` branch, matched on the authored
line, and does the same bookkeeping `Set` does, with `source: 'generated'`:

- **CLI** (`src/runner/test-runner.ts`): the main-flow branch beside `Set`,
  and the hook-scope dispatch beside its `Set` case. The console line is
  `[ai] random_name = "AUTO4821"`, masked.
- **Sessions API** (`src/server/session-manager.ts`): inside the same `try`
  as the `Set` branch. It writes `session.outputs` and `outputSources`,
  emits `capture`, and puts the value in the HTTP result's `outputs`. The
  mapping found that a `Set` row's `results[].outputs` comes back `{}` while
  the report row keeps it. `[use ai]` must carry the value in both, and the
  implementer should say whether the `Set` behaviour is intended.
- **Errand** (`src/server/errand-runner.ts`): the branch beside `Set`; the
  run-time `[use …]` refusal learns to let `[use ai]` through.
- **Electron** (`src/ui/main/runner-adapter.ts`): the branch beside `Set`.

`tests/run-loop-contracts.test.ts` forbids bare `resolvedParameters[x] =`
writes and `tests/substitution-sites.test.ts` counts `interpolate(`-family
calls per file. Both will notice the new sites; update their tables rather
than working around them.

### MCP

- `assembleSteps` gets the new `useStepError` for free.
- `run_errand` allows `[use ai]` steps.
- `missingParameters` (`src/mcp/assemble.ts`) subtracts a `[use ai]` step's
  explicit names and, for a step with none, every later `{{x}}` whose name
  appears in that step's text as a whole word. That is the same rule the
  runtime name check enforces, so the pre-flight warns exactly when the run
  would fail.
- `STEP_SYNTAX` and the `run_steps` / `run_errand` schema descriptions gain
  one line each.

### runner-core and TestBench

- The `use-step.ts` mirror and the `CaptureEvent.source` union (above).
- **Diagnostics** (`section-diagnostics-core.ts`): no squiggle on a valid
  `[use ai]` line, and the new refusals shown where the parser shows them.
- **Completion** (`useDirectiveCompletions`): offers `[use ai]` with the
  detail *ask the model for a value*, not *surface switch*.
- **`classifyDebuggableLine`**: a `[use ai]` line must not classify as
  `'plain'`, since Step Into on a plain line pauses in compiled code and
  this step never has any. Classify it as `'use'`.
- **`CAPTURE_PATTERNS`**: already catches `[store as: x]`. Prose names are
  deliberately not scanned today and stay unscanned, so completion and F12
  know a `[use ai]` value only when its name is explicit. The docs say so.
- **Variables panel** (`variables-panel.js`): seeds a row for an explicit
  `[use ai]` name before a run with source `generated`, and
  `classifyCaptureSource` learns `'generated'`.
- Patch bump in `testbench-native/package.json`.

## Tests

- **Parser, both copies:** accepted forms (case, colon, `[no-hooks]`,
  each explicit-name spelling) and every refusal in §Design, through the
  parity table.
- **`parseUseAiReply`:** the two shapes; a number; a boolean; an array; an
  object; both keys; neither; fenced JSON; prose around JSON; an empty or
  whitespace value.
- **Shared runner, with a fake `AiClient` that records the messages it
  receives:**
  - the user message is exactly the resolved, masked text;
  - an unresolved reference makes no call;
  - an explicit name overrides `as`;
  - the whole-word check, passing and failing;
  - `error` is not retried and a malformed reply is;
  - a secret-named value arrives as `***`, and an `unmask:` name arrives
    as its value.
- **Per loop, modelled on the `Set` tests:**
  - the CLI main flow and a hook;
  - the Sessions API at the HTTP seam, covering the `capture` event
    `source`, `session.outputs` and the HTTP result's `outputs`;
  - the errand receipt;
  - the Electron adapter.
- **Cache and compile:** a run twice with caching on makes two model calls
  and writes no cache entry for the step; each compile classifier reports
  the reason; a hand-written `.steps.ts` entry for the step's text is not
  run.
- **Grouper and computer lock:** an `If` step followed by a `[use ai]` step
  does not group them; `stepReadsScreen` is false for it.
- **MCP:** `missingParameters` with explicit and prose names.
- **runner-core:** a `node --test` case for the widened union.
- **TestBench:** diagnostics, completion and the Variables panel source.

### Live

A fixture `templates/init/tests/use-ai-live.md` against the fixture app,
and `testbench-native/tests/integration/live/use-ai.test.cjs` driving it
through TestBench. It should prove, with the real model:

- a prose-named value and a `[store as:]`-named value both reach later steps;
- a `[use ai]` value is typed into a page field and read back;
- the `capture` events carry `source: 'generated'`;
- the report's ◆ Captured box shows the values;
- a second run asks the model again and paints a plain pass, never a cached
  or compiled one.

Assertions on the model's output check shape (eight digits, starts with
`AUTO`), not exact values: a wrong date from correct inputs is the model's
arithmetic, not a framework defect, and the test should log it rather than
fail on it.

## Not in this story

- **Lists.** `{"value": [...]}` to feed a `For each`. Nobody has a use for
  it yet.
- **Caching, compiling, seeding, temperature control.** All were
  considered; the user's rule is that determinism is a tool's job.
- **A built-in date, time or random value.** See §Context.
- **The per-step surface prefix** `[use computer] Click Save`. Still
  deferred in SPEC-use-computer §12.
- **`[use ai]` as a control-line tail.** Refused with a message.
- **Completion and F12 for prose-named values.** Explicit names only.
