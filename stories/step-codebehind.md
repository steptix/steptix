# Step code-behind

## What we're building

Every natural-language step in a test can carry a piece of Playwright
TypeScript — its **code-behind** — stored in a committed sibling file next to
the test. When a step has code-behind, the runner executes that code instead
of asking the AI. When it doesn't (new step, edited step, or the code just
broke against a changed page), the AI runs the step as today and — if
generation is enabled — writes the code-behind for next time.

The result: the first run of a test costs AI tokens; every run after that is
straight-line Playwright code. Zero model calls, seconds instead of minutes,
and it stays correct for steps the action cache fundamentally cannot replay.

Example. `tests/booking.md` contains:

```markdown
5. Enter todays date as a 6 digit code in ddmmyy format
```

- **Run 1 (AI, ~8s for this step)** — the model works out today is 22/08/26,
  types `220826`, the step passes, and this entry appears in
  `tests/booking.steps.ts`:

  ```ts
  {
    source: 'Enter todays date as a 6 digit code in ddmmyy format',
    async run({ page }) {
      const d = new Date();
      const code = [d.getDate(), d.getMonth() + 1, d.getFullYear() % 100]
        .map((n) => String(n).padStart(2, '0'))
        .join('');
      await page.locator('#booking-code').fill(code);
    },
  },
  ```

- **Run 2 onward (<1s, zero tokens)** — the runner executes that function.
  The date is recomputed at runtime, so it is right today, tomorrow, and next
  year.

Contrast with the step cache, which replays the recorded literal action
`{ "action": "type", "selector": "#booking-code", "value": "220826" }`
forever — tomorrow it types yesterday's code, and if the app accepts any
six-digit value the test *silently passes with wrong data*.

Because the file is plain TypeScript bound to steps by their text, it is also
reviewable, diffable, hand-editable, and shared across machines and CI via
git — none of which is true of `.cache/`.

## Context — why the action cache isn't enough

The step cache ([src/cache/step-cache.ts](../src/cache/step-cache.ts) (since removed)) stores
the AI's parsed action plan — literal selectors and literal values — and
replays it with the model bypassed. That already gives "zero AI on run 2",
but a flat action list cannot express *compute this at runtime*, and its only
notion of variable data is reverse-interpolating `{{param}}` values back into
strings, which has known failure modes:

- [issue 023](../issues/023-cache-reverse-interpolation-substring-collision.md) (since removed) —
  blind `replaceAll` corrupts incidental substrings.
- [issue 024](../issues/024-cache-value-driven-element-targeting-rides-cache.md) (since removed) —
  a param that should change *which element* is targeted replays the frozen
  selector from run 1.
- Derived values (dates, computed codes, anything the AI worked out) are
  frozen at record time with no marker that they were ever dynamic.

The assertion code cache already landed the fix one
level down, and its core insight generalises verbatim:

> The "result" worth caching isn't a pass/fail outcome — that changes per
> run. It's the **verification method**.

This story lifts that from assertions to whole steps: cache the *method* as
code. Real variables replace string surgery (fixes 023), code can derive a
selector from a parameter (fixes 024's class of bug), and dynamic values are
computed on every run.

It is also the natural completion of the tools story
([tools-with-playwright-access.md](tools-with-playwright-access.md)): tools
are deterministic TypeScript the *author* writes; code-behind is
deterministic TypeScript the *AI* writes, running on the same substrate.

## Design

### The code-behind file

One file per markdown file, committed, sibling to it:

| Markdown | Code-behind |
|---|---|
| `tests/github.md` | `tests/github.steps.ts` |
| `skills/login.md` | `skills/login.steps.ts` |

A skill's code-behind lives beside the *skill*, so every test that calls the
skill shares it. (This is strictly better than the action cache, which
disables caching for non-root frames to dodge the key-collision problem in
issue 037.)

The file default-exports `defineSteps([...])`, imported from a new
`steptix/codebehind` subpath (same pattern as `defineTool` from
`steptix/tools`):

```ts
// Generated by Steptix — code-behind for github.md.
// Safe to hand-edit: entries match steps by their `source` text.
// A step whose text changes falls back to AI and is regenerated.
import { defineSteps } from 'steptix/codebehind';

export default defineSteps([
  {
    source: 'Enter the username {{username}}',
    async run({ page, step }) {
      await page.locator('#login_field').fill(step.getVar('username')!);
    },
  },
  {
    source: 'Get a list of the names of the top repositories on the left panel [as: repos]',
    async run({ page, step }) {
      const names = await page
        .locator('aside [data-testid="repository-list"] a.repo-name')
        .allTextContents();
      step.setVar('repos', names.map((n) => n.trim()).join(', '));
    },
  },
  {
    // A step defined inside `### Checkout` in the same markdown file.
    section: 'Checkout',
    source: 'Click the Pay now button',
    async run({ page }) {
      await page.locator('button[data-testid="pay-now"]').click();
    },
  },
  {
    // Author escape hatch: this step always runs under AI,
    // and generation never touches this entry.
    source: 'Verify the dashboard looks correct',
    ai: true,
  },
]);
```

`defineSteps` is an identity function providing types, like `defineTool`.

**Binding.** An entry's `source` is the step's raw markdown text as
authored: everything after the list marker, trimmed, exactly as written in
the `.md` — including `{{param}}` placeholders, `[as: x]` markers, and any
`[no-hooks]` marker — before any interpolation or skill-scope transform.
This is precisely the "match side" the sections feature already froze: the
parser retains untransformed `rawSteps` at every level (main flow, section
bodies, skill bodies), accessed through `matchInput`
([src/parser/section-match.ts](../src/parser/section-match.ts)) with the
contract's `rawSteps?.[i] ?? steps[i]` fallback on the server path, where
incoming steps are already raw form. Code-behind binding MUST reuse that
accessor — it must not add a seventh hand-rolled scanner
([issue 035](../issues/035-step-line-span-parser-duplicated-six-times.md)).
Unlike section-call matching, comparison is **case-sensitive** exact
equality after trimming: an edited step should miss and regenerate, not
fuzzily match.

- Step with a matching entry → runs as code.
- Step with no matching entry (new step, or its text was edited) → AI, then
  regeneration if enabled. Nothing else in the file is touched — per-entry
  validity, deliberately unlike the cache's whole-bundle `stepsHash` where
  one edit deletes everything.
- Entry matching no step → load-time warning, ignored at runtime, never
  deleted by the writer.
- Entry with `ai: true` → step always runs under AI; generation skips it.
- Entry with neither `run` nor `ai: true` → load-time warning, dropped from
  the index; the step misses, runs under AI, and regenerates.

### Sections and skills — which file, which scope, which occurrence

Steps don't only live in a test's main flow: they live in `### Section`
bodies (inlined at every call site by the expander) and in skill bodies
(inlined per invocation, with per-invocation variable renames). Binding has
to be exact about all three, and the expander already computes everything
needed: every expanded step carries an origin frame
(`ExpandedStepOrigin.frameId` → `ExpandedFrame`, kinds
`test | skill | section`, mirrored server-side as `FrameInfo`), where a
frame's `uri` is the file that *defines* its steps and, for section frames,
`skillName` carries the section name.

**Resolution rule.** For each expanded step, the *nearest enclosing frame*
decides where its code-behind lives and what scope it matches in:

| Nearest frame | Defining file | Entry must have |
|---|---|---|
| top level (`''`) | the test file | no `section` field |
| `kind: 'skill'` | that skill's file | no `section` field |
| `kind: 'section'` | the frame's `uri` (test file, or the skill file for a skill-internal section) | `section` = that section's name (compared with the contract's `matchText`) |

So a test-file `### Checkout` body step binds to an entry
`{ section: 'Checkout', source: '...' }` in the *test's* `.steps.ts`, and a
section defined inside a skill binds inside the *skill's* `.steps.ts`. A
section-call line itself (`3. Checkout`) expands away and is never bound,
executed, or generated; likewise `[skill:]` / `[tool:]` bracket steps.

**Occurrence counting is per frame instance, not global.** A section or
skill body is *defined once* but *inlined many times*. Every invocation is
its own frame, and matching restarts per frame — so all invocations of
`### Checkout` bind to the *same* entries, in body order, and a duplicated
"Click Next" inside one body matches its two entries by order within that
body. Two consequences worth stating:

- Generation writes a section/skill body's entries once; the second
  invocation (or the tenth test calling the skill) finds them already valid.
- Binding is completely insensitive to how many calls precede a step, which
  frame counter it got, or whether the run is a Steptix subset batch — the
  exact instabilities that forced the action cache to disable caching for
  non-root frames ([issue 037](../issues/037-cache-key-shifts-between-batches.md)).

**Skill variables — the frame-aware `getVar`.** Inside a skill body the
author writes `{{username}}`, but `applySkillScope` rewrites each
invocation's step *text* to `{{__skill<N>_username}}` and the runtime
parameter map holds the namespaced key. Generated code must keep using the
**authored** name — it is generated once per skill, not per invocation — so
`ctx.step.getVar` / `setVar` are frame-aware: for a step executing inside
skill frame N, `getVar('username')` resolves through that frame's namespace
first (the same `__skill<N>_` mapping the expander applied to text, plus
output aliasing on writes — precedent in the tool executor,
[src/tools/executor.ts](../src/tools/executor.ts)), then falls back to the
bare name. The generation prompt receives the authored raw text, so it
naturally emits authored names; the runtime does the mapping. Skill-internal
sections compose: frame chain `skill → section` gives the skill file for
resolution *and* the skill frame for variable scope.

**Concurrent writers.** A skill's `.steps.ts` is shared, and two server
sessions could heal the same skill step at once. Writes are atomic
(write-temp + rename), esbuild-validated before replace, and last-writer
wins — both writers are writing code for the same authored step, so either
result is valid.

### Execution

Resolution happens at test load, *after* skill/section expansion, where both
the authored raw text and the origin frames are still in hand: for each
expanded step, the nearest-enclosing-frame rule above names the defining
file and scope, and the sibling `.steps.ts` of that file is consulted. The
alignment (step index → entry or nothing) is computed once here and carried
into the executor as a registry, like `stepCache`. Each file is
imported with the same esbuild bundle-per-load mechanism the tool layer uses
([src/tools/reload.ts](../src/tools/reload.ts)) — temp module co-located next
to the source (a `node_modules` path segment breaks the package
self-reference), `absWorkingDir` set so sourcemaps allow step-into from a
debugger. Each distinct `.steps.ts` is loaded once per run, however many
frames resolve to it.

Per step, the order in the executor's existing pre-AI short-circuit
([src/runner/step-executor.ts:279](../src/runner/step-executor.ts)) becomes:

1. **Code-behind entry?** Run it. No model call, no DOM snapshot capture, no
   stall detection — the same bypasses a cache hit gets today.
2. **Action cache hit?** Replay as today. (A step that ran as code neither
   reads nor writes the action cache.)
3. **Neither** → normal AI flow.

The `run` function receives the same `ToolContext` the `[tool:]` layer builds
([src/tools/types.ts](../src/tools/types.ts)) — live `page` / `context` /
`browser`, `step.getVar` / `setVar` / `expect`, `log` — plus `baseUrl`. Same
two guarantees as tools: same live Playwright instances the AI loop drives,
and the variable scope is the same map `{{var}}` and `[as: x]` use. Execution
honours the session abort signal and the same timeout discipline as tool
steps.

> **Extended by [codebehind-env-data.md](codebehind-env-data.md).** The
> variable map never held the environment — `${data.url}` is substituted by
> the parser before the run — so `step.getVar` had no way to read it.
> `getVar` now falls through to the run's env/data context for a name
> written the way the placeholder is: `step.getVar('data.url')`,
> `step.getVar('env.BASE_URL')`. Parameters still win.

**Failure → self-heal.** If `run` throws, the runner logs
`Code-behind failed for step N — falling through to AI`, discards that entry
for the rest of the run, and enters the normal AI flow with a clean slate —
the page is already in the right state, exactly the contract the cache's
invalidate-and-fall-through has at step-executor.ts:303. A `step.expect`
failure is a *real* step failure, not a fall-through — same rule as the
assertion code cache: broken code heals, a failed assertion fails.

**Reporting.** The step result carries `fromCodeBehind: true` (sibling of
`fromCache`), rendered with its own glyph (`</>` next to the cache's `⚡`), plus
the entry's code in a collapsed block (as `assertionCode` renders today) and
any `log` output — the tool-step outcome shape already covers this.

### Generation

> **Superseded by [codebehind-compile.md](codebehind-compile.md).** Inline
> generation during runs and the `codebehind.generate` key are removed;
> generation becomes an explicit compile with whole-test context, a review
> pass and replay-to-green. A failed entry now heals through AI and is
> flagged `codeBehindStale` for the next compile. The mechanics below
> (prompt inputs, rules, the leak guard, the writer) survive as building
> blocks of the compiler; the trigger does not.

Gated by config, default off:

```json
{ "codebehind": { "generate": true } }
```

*Execution* needs no flag — a `.steps.ts` file present next to a test is the
author's intent, like a `tools/` directory. *Generation* writes files into
the author's project, so it is opt-in.

When enabled, at the point where the cache writes today (step success,
step-executor.ts:348): if the step ran under AI and has no valid entry (or
its entry just failed and was healed), make **one** additional model call.
The prompt contains:

- the raw step text (with `{{param}}` placeholders),
- the parameter names and their current resolved values (so the model can map
  literals in the transcript back to `step.getVar('name')` calls),
- the successful action transcript for the step — the same `AIAction[]` the
  cache stores, selectors included,
- assertion conditions and results, if the step had any,
- the `run(ctx)` contract and the rules below.

The model returns `{"entry": "<the full entry object literal, as a string>"}`
— the AI client forces `responseFormat: json_object`, so the response is the
same JSON envelope the assertion code cache uses, never a bare fenced block
(a live-run lesson: the first cut asked for fenced TS and every generation
was refused); the runner stamps the `section` field
itself from the step's frame — the model never chooses scope. For a
frame-scoped step, generation targets the *defining* file's `.steps.ts`
(skill or test), so healing a skill step from one test fixes it for every
test. Rules enforced by the prompt:

1. **Parameters are read via `step.getVar`, never inlined.** A
   post-generation guard rejects any generated code containing a resolved
   parameter value as a literal — this is what keeps `{{password}}` out of a
   committed file. Values shorter than 3 characters are exempt: "1" or "AU"
   occurs incidentally in nearly any code, and nothing that short is a
   secret.
2. **Dynamic values are computed at runtime** — dates, derived codes,
   anything the step text describes as a computation rather than a constant.
3. **Outputs are written**: `[as: x]` captures become `step.setVar('x', ...)`.
4. **Assertions become code**: `step.expect(cond, message)`.
5. **Web-first waiting**: rely on locator auto-waiting; add
   `locator.waitFor()` where the recorded run needed explicit waits; no bare
   `page.waitForTimeout` unless the recorded run required one. (Code runs far
   faster than AI think-time — this is the classic codegen flake and the
   prompt must defend against it.)
6. **No imports** beyond what the entry receives via `ctx`.

**Steps that stay AI.** Generation is skipped (no entry written, step keeps
running under AI/cache) when the successful transcript used framework-level
actions that mutate runner state rather than the page: `openBrowser`,
`switchBrowser`, `closeBrowser`, `openPage`, `closePage`, `switchPage`,
`prompt`. `[skill:]` / `[tool:]` steps and section-call lines never reach
generation at all — they are dispatched or expanded before the AI loop. But
`[output:]`, `[input:]` and `[interactive]` steps *do* reach the executor
with their marker intact, and generation explicitly refuses them: a
generated entry could silently stop performing the capture or prompt the
marker exists for. (A hand-written entry for such a step still executes —
the refusal is generation-side only.) Everything else — including
`api_call`-style work, which becomes `ctx.context.request` code — is fair
game.

**The writer.** Regeneration must not clobber hand edits elsewhere in the
file:

- Locate the entry to replace by its `source` string literal **and** its
  `section` property (a main-flow `Click Next` and a `### Checkout`
  `Click Next` must not rewrite each other; nth occurrence disambiguates
  duplicates within one scope), then take the enclosing `{ ... }` span with
  a small tokenizer that tracks strings, template literals, and comments
  while brace-matching.
- Replace only that span. New entries append before the closing `])` of the
  default export, in step order. No file → create from the header template
  above.
- After every write, validate by esbuild-bundling the result. If the bundle
  fails, restore the previous content byte-for-byte and log a warning —
  the writer must never leave a file it broke.
- The writer never deletes entries — not even ones matching no step.

### Server path

Steptix and the Sessions API route through the same
`executeStep`, so execution works as soon as the session's step options carry
the per-step lookup. Two server specifics:

- Code-behind files resolve relative to the *test file's* project, riding the
  same per-request bundle resolution as `steptix.config.json` / `.env`
  ([src/server/project-bundle.ts](../src/server/project-bundle.ts)).
- `codebehind.generate` must be threaded through `resolveProjectBundle`, not
  read off startup config — the known trap where per-project values silently
  no-op on the server path.

## Implementation outline

New code:

- `src/codebehind/types.ts` — `StepCodeEntry` (with optional `section` and
  `ai`), `CodeBehindContext` (= `ToolContext` + `baseUrl`), `defineSteps`.
- `src/codebehind/loader.ts` — defining-file resolution from the expansion's
  frames/origins (nearest-enclosing-frame rule), bundle-import (generalising
  `bundleAndImport` from [src/tools/reload.ts](../src/tools/reload.ts)),
  entry↔step alignment using `matchInput`
  ([src/parser/section-match.ts](../src/parser/section-match.ts)) with
  per-frame-instance occurrence counting, unmatched-entry warnings. Produces
  a registry passed into step options like `stepCache`. No new step/section
  scanner of any kind (issue 035).
- `src/codebehind/writer.ts` — tokenizer, span replace / append / create,
  esbuild validation with restore-on-failure.
- `src/ai/prompts.ts` — `buildStepCodePrompt` (precedent:
  `buildAssertionCodePrompt`); parse in `src/ai/action-parser.ts`; the
  literal-parameter-value guard beside the parser.

Three additive shape extensions carry what binding needs past
`parseTestFile`, none of which survives parsing today:
`SkillExpansion.rawSteps` (post-expansion authored match text, built with
`matchInput`), `ExpandedFrame.varScope` (the `__skill<N>_`/alias table
`applySkillScope` applies to text, consumed by the frame-aware `getVar`),
and `ParsedTest.expansion` (`rawSteps`/`origins`/`frames`, synthesised even
for files that never enter the expander). Loader temp bundles go in a
gitignored `.steptix-codebehind-cache/` beside the `.steps.ts` (never under a
`node_modules` segment); a test with no code-behind file pays no esbuild
load and gets no stray dot-dir.

Modified code:

- `src/runner/step-executor.ts` — code-behind branch ahead of the cache
  attempt; ctx build + execution on the tool substrate
  ([src/tools/executor.ts](../src/tools/executor.ts) internals reused, not
  duplicated), with the frame-aware `getVar`/`setVar` view for skill-frame
  steps; fall-through + regeneration call on the success path.
- `src/runner/test-runner.ts`, `src/server/session-manager.ts` — load the
  registry at test load and pass it through (the same two places the step
  cache is wired). Errand runner, Electron adapter, and REPL take the
  parameter but may pass `undefined` in v1.
- `src/config/defaults.ts` + config types — `codebehind: { generate: false }`.
- `src/server/project-bundle.ts` — carry `codebehind` per project.
- `src/report/types.ts` / `generator.ts` / `template.ts` —
  `fromCodeBehind`, code block, `</>` glyph.
- `package.json` — `"./codebehind"` export subpath.

## Tests

- `tests/codebehind-alignment.test.ts` — binding: exact match, duplicates by
  occurrence, edited step misses, reorder keeps matches, unmatched entries
  warn, `ai: true` short-circuits. Sections: a `### Checkout` body step binds
  only to a `section: 'Checkout'` entry; a section invoked twice binds both
  invocations to the same entries; occurrence counting restarts per frame
  instance; a section-call line binds to nothing. Skills: a skill invoked
  from two tests resolves to the skill's own `.steps.ts`; a skill-internal
  section resolves to the skill file with the section scope; binding goes
  through `parseTestFile` + expansion, not hand-built arrays (the contract's
  §2.3 lesson — hand-built inputs bypass the transforms that cause the
  bugs).
- `tests/codebehind-vars.test.ts` — frame-aware variables: inside a skill
  frame, `getVar('username')` resolves the `__skill<N>_`-namespaced key and
  falls back to the bare name; `setVar` honours output aliasing; two
  invocations of one skill each see their own values from the same entry.
- `tests/codebehind-writer.test.ts` — replace one entry with braces inside
  strings/templates/comments elsewhere in the file; append; create from
  template; hand-edited helper code outside entries survives byte-for-byte;
  esbuild-validation failure restores the original.
- `tests/codebehind-generate.test.ts` — prompt parse, and the guard: code
  containing a resolved param value (e.g. a password) is rejected.
- Integration fixtures (pattern of `fixtures/tests/assertion-cache.md`, since removed):
  - a test with a complete hand-written `.steps.ts` runs with **zero AI
    calls**;
  - an entry that throws falls through to AI and the test still passes;
  - with `generate: true` and a fake AI client, run 1 writes the expected
    `.steps.ts` and run 2 replays it with zero AI calls.

## Non-goals (this story)

- **Standalone `.spec.ts` export** — stitching per-step entries plus a small
  runtime shim (ctx, `.env` reading, launch profile: locale, timezone,
  stealth channel) into a file `npx playwright test` can run with no server.
  The entry format here is deliberately shaped so that export is close to
  concatenation. Separate story.
- **Steptix UI affordances** — `fromCodeBehind` rides the existing step
  result JSON; no extension change, no version bump.
- **Proactive drift detection** — code fails, then heals; same stated
  non-goal as the assertion code cache.
- **Code-behind for hooks and `[output:]` steps**, and wiring the errand /
  Electron / REPL entry points — mechanical follow-ups once the registry
  exists.
