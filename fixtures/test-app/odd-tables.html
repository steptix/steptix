Legacy screens

Four shapes no structural rule can read: headings written as ordinary cells, a column key that comes after the report, a list drawn as cards, and one small table per record. Each is what an older business screen actually looks like, and each is answered by asking the model about the structure once.

Payees

A <table> with no <thead> and not one <th>. The first body row is <tr><td><b>Payee</b></td>… and CSS gives it a grey band, so it reads as a heading to a person and is an ordinary data row to the markup. Why structure cannot decide: §7.3 has nothing to map — no header row exists — so a read that names Payee or Amount fails for a shape reason, and a rule that promoted the first row on sight would eat a record from every headerless table in the app (scheduled-payments.html has five records and no heading row at all). A read by position already works here today (§4.4): six rows, three columns, the first row being the heading is the author's problem. What the model is asked (§7.10): one question, with a sketch of the region, answered as {"kind": "table", "rows": "T1", "header": {"table": "T1", "row": 1}} — row 1 of this same table is the header. Validation then checks that row 1 names at least one column, that the widths agree and that every requested name resolves, and the read returns the 5 payees under Payee, Reference and Amount. The mapping is cached, so the model is asked once and never again while the page keeps this shape.

Account summary

The rows come first, in a table with no header of its own, and the header arrives afterwards as a table of nothing but a <thead> — with a Column key paragraph between the two. Why structure cannot decide: §7.3a pairs a header-only table with a rows table when they are contiguous siblings and the header comes first; here the order is reversed and a paragraph sits in the gap, so the sibling rule never fires and the read fails for a shape reason rather than guessing. Nothing here is broken — it is what a report looks like when somebody bolted a key onto the bottom of it years later. What the model is asked (§7.10): the sketch shows two candidates, and the answer is {"kind": "table", "rows": "T1", "header": {"table": "T2", "row": 1}} — read the first table's rows under the second table's header row. Validation checks that T1 has data rows, that T2's header row names columns and that the two widths agree (three and three), and the read returns the 4 accounts under Account, Balance and Status. Note the pair is only decidable by reading the words: swap the header's labels and no structural signal changes at all.

Accounts as cards

Six repeated <div class="account-card">, each with an <h3 class="card-title"> holding the account's name and a <div class="fields"> of <div class="field"> rows, each one a <span class="label"> / <span class="value"> pair for Balance, Status and Owner — so the Account column comes off the title and the other three off the pairs. Why structure cannot decide: there is no <table>, no role, no row and no cell anywhere — not a table the rules read badly, but nothing for a table rule to fail on. The read refuses with "found no table with rows", which §7.10 treats as a shape reason. What the model is asked: a collection, not a table — {"kind": "collection", "item": ".account-card", "fields": {…}}, one selector for the repeated element and one per requested column, each relative to the item. Validation checks the item selector matches between 1 and 500 elements with none nested inside another, and that each field selector matches at most one element per item; a field that matches in no item fails the read, and one that matches in some reads "" in the others and is counted in the log. Extraction gives one record per rendered item in document order, each with _row. The last card is hidden with display:none — a closed Travel account — so a correct read returns 5 records from 6 matching elements, the same way §7.4 drops a hidden row, and _row runs 1…5 with no gap for it. The balances, statuses and owners here are deliberately not the ones in Account summary above, which lists the same account names: were they the same, a read that resolved the wrong region would satisfy the other region's verify and the test would pass on the wrong markup.

Payment property sheets

Four payments, each drawn as its own two-column table: the field name in a <th scope="row"> and the value in the <td> beside it, four rows — Payee, Reference, Amount, Status — per record. Why structure cannot decide: the problem is not that the tables are unreadable, it is that they are readable and give the wrong answer. Name one and a read returns four rows of two columns — the record on its side. Name the #property-tables wrapper and §7.2 finds four tables with rows and refuses as ambiguous, with the sentence about frozen columns. Both are shape reasons, so both reach §7.10. What the model is asked: again a collection, with the item being the table and each field one of its rows, as {"kind": "collection", "item": "…", "fields": {"payee": "tr:nth-child(1) td", …}}. The sketch lists these four by the paths the runtime derived for them — :scope > table:nth-of-type(1) through (4) — so the item selector usually comes back in that shape rather than as the class selector table.property-table, and nothing depends on which spelling it picks. What matters, and what validation checks, is that it matches one element per record: four here, none nested inside another, at most one element per field per item. A path that named a single nth-of-type table would validate and read one record rather than four, which is why the test below verifies the count. A correct read returns 4 records with _row 1…4, in document order, and the cached mapping means the next run does it without asking. The payees here are deliberately not the payees of Payees above: both sections are read for a Payee and an Amount, and identical values would let a read of the wrong region pass the other's verify.
