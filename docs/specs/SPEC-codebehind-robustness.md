# Compiled code-behind that holds up on replay

**Status:** spec, for build. Four phases; Phase 1 is small.
**Opened:** 2026-10-07
**Written against:** `main` at `62348262`. Line numbers are as of that
commit. Treat them as pointers, and find the code again if it has moved.
**Decided:** D4, D6 and D7 were approved by the project owner on 2026-10-07.
The other decisions in §5 are this spec's proposals. §9 lists what is still
open, each with the default to build.

## 1. What this is

Run & Compile turns a test's AI-driven steps into Playwright code, so that
later runs replay the code instead of asking a model. The code is written
once, committed, and trusted by every run after it.

Two live tests showed that code going wrong in two different ways (§3):

- **It does not wait for what its own click caused.** A compiled sign-in
  clicked, declared success 57 ms later while the login request was still in
  flight, and the next step judged a page that had not changed yet.
- **It reads something other than what the AI read.** A compiled read
  dropped one selector token and captured six values where the AI run had
  captured three.

Both pass under AI and fail only on replay, so the author finds out on a
later run, not when they compile. Behind the first sits a third finding: the
wait the AI path uses after every action cannot see network work at all
(§3.3).

This spec fixes both failures and the classes they belong to, in four phases
(§6). Phase 1 is three small changes, one per root cause. Phase 2 closes the
classes. Phase 3 improves what the generator sees and what a ⚠ says. Phase 4
is a measured experiment. §7 is for whoever builds it: order, conventions and
the baseline to compare against.

## 2. How compiled code-behind works today

Terms used below:

- An **entry** is the code for one step in `<test>.steps.ts`.
- **Replay** is a later run that executes the entries.
- An entry **heals** when its code throws: the step runs under AI instead,
  and is marked ⚠.
- An **acting** entry performs an action on the page: a click, a fill, a
  navigation and so on. A **read-only** entry only reads. §6.3 defines the
  difference mechanically.

### 2.1 Compile

Run & Compile runs the test under AI and records every step: its actions,
what the runtime measured about each target (`targeting`), and the page
before and after. While the run carries on, a model writes one entry per step
(`src/codebehind/live-compile.ts:56-80`); the browser never waits for it.

Each entry passes a set of static checks that share one re-ask
(`src/codebehind/generate.ts:461-527`): ambiguous selectors, literal upload
paths, undeclared context properties, stale tab handles, and reads that
assert without waiting. At the end of the run a **Review** pass rewrites the
whole file in one model call (`src/codebehind/review.ts:234-310`). Apply
writes the file.

Generation has three outcomes: an entry; a decline, written as an `ai: true`
entry with the reason; or an error. In Run & Compile an error leaves the step
on AI with no entry, notes why, and the next compile takes the step again
(`live-compile.ts:1732-1745`); the summary counts it as "N step(s) could not
be generated; they stay AI" (`live-compile.ts:1946`). In the CLI
`steptix compile`, an error fails the whole compile (`compile.ts:981-994`).

A step whose entry threw on an earlier run is regenerated by a separate
**repair** prompt, which shows the model the failing code and its error:
`askForRepair` in Run & Compile (`live-compile.ts:1551-1559`, `1605-1676`)
and `repairHealedStep` in the CLI compile (`compile.ts:929`). Repair answers
get the leak guard but none of generation's static checks.

Nothing runs the code before Apply. That is a recorded decision, "Proof, not
Replay" (`stories/compile-as-you-go.md:227`): an entry is born unproven, and
the next run is its proof. Only the CLI `steptix compile` replays, in strict
rounds (`src/codebehind/compile.ts:1213-1460`).

An entry, as the compile in §3.1 wrote it:

```ts
{
  source: 'Navigate to the baseUrl',
  async run({ page, step, baseUrl }) {
    await page.goto(baseUrl);
    const targetUrl = new URL(baseUrl).href;
    step.expect(page.url() === targetUrl, 'Page navigated to the baseUrl');
  },
},
```

`If`/`While` lines compile to `async condition({ page, step })` entries that
return true or false. A step can also be kept on AI with `ai: true`, which is
the author's opt-out: compile never regenerates it (`live-compile.ts:447`,
`555`).

### 2.2 Replay

A step with an entry runs the entry instead of the model:

| What the entry does | Result |
|---|---|
| Returns | ✓ `</>`: passed as code |
| Throws (a selector timeout, a `ReferenceError`, …) | Heals: the step runs under AI and shows ⚠ (`pass-stale`). The entry is discarded for the rest of the run and marked stale, so repair picks it up |
| A `step.expect` fails | The step fails. No heal |

The rule is "broken code heals, a failed assertion fails"
(`stories/step-codebehind.md:274-280`; `src/runner/step-executor.ts:1364-1381`).
Compile's strict replay and keyless runs never heal.

### 2.3 Who waits for the page

| Moment | AI path | Compiled path |
|---|---|---|
| After each action | `waitForPostActionSettle` (`src/browser/page-state.ts:269`): waits for the URL and a DOM fingerprint to be quiet for 600 ms; gives up after 1.2 s of no change; caps at 3.5 s | Nothing. `runCodeBehindEntry` awaits `run` and moves on (`src/codebehind/execute.ts:286-293`) |
| Before judging `If … then return / stop / fail` | Up to 10 s for 1 s of DOM quiet (`step-executor.ts:2417-2437`; `stories/step-flow-control.md`, decision 6) | Nothing (`step-executor.ts:854-863`) |
| Before judging `If` / `While` | The same 10 s / 1 s (`step-executor.ts:4443`) | The same, via `settleBeforeConditions` (`step-executor.ts:1291-1303`; `src/runner/control-runtime.ts:882`) |
| Between turns | Seconds of model think time | None |

The comment on the AI path's wait before a return describes failure A
exactly (`step-executor.ts:2420-2422`): a title read just after the click
that changes it is the stale answer that makes the return miss.

## 3. The failures

The evidence comes from two full live runs: on 2026-10-06 at `main`
`6ab73e80`, and on 2026-10-07 at `75ec40db` plus fixture edits equivalent to
those PR #14 later merged, which touch neither failure. The shard logs under
`.live-shards/` are temporary and are gone; everything needed is quoted
below. Both runs predate PR #14, which changed one line of failure A's
fixture (§3.1).

### 3.1 Failure A: the sign-in that does not wait

**Test:** `steptix-vscode/tests/integration/live/flow-control.test.cjs`,
"compiles the return to step.exit() and returns as code on replay". Failed in
both full live runs.

**Fixture:** `templates/init/tests/flow-control-live.md` calls one section
twice. The first call signs in; the second should find the Dashboard and
return at once:

```markdown
## Steps
1. Navigate to the baseUrl
2. Sign in
3. Sign in
4. If the page title contains "Dashboard" then stop running the remaining steps
5. Click "Sign out"

### Sign in
1. If the page title contains "Dashboard" then return      ← line 29
2. Reject non-essential cookies in the cookie banner       ← line 30
3. Enter the username {{username}}                         ← line 31
4. Enter the password {{password}}
5. Click the Sign in button                                ← line 33
```

That is the fixture as the runs saw it. PR #14 has since made line 30
`If the cookie banner is shown, then Reject non-essential cookies in the
cookie banner`, so the replay's ⚠ on line 30 below is no longer where it
fails. It changes where the failure shows, not its cause: line 29's
compiled return still reads the title tens of milliseconds after the click.
Reproduce A on current `main` before starting (§7).

**What the page does.** Sign In does not navigate by itself. The page POSTs
`/api/login`, and only when that answers does it set
`window.location.href = 'dashboard.html'`
(`fixtures/test-app/index.html:261-279`).

**The compiled entries:**

```ts
// line 33 — Click the Sign in button
async run({ page, step }) {
  await page.locator('#sign-in-btn').click();
  const dashboard = (await page.title()).includes('Dashboard');
  const signInFormVisible = await page.locator('#email').isVisible();
  step.expect(
    dashboard || signInFormVisible,
    'Sign-in attempt reached the dashboard or left the sign-in form available',
  );
},

// line 29 — If the page title contains "Dashboard" then return
async run({ page, step }) {
  if ((await page.title()).includes('Dashboard')) step.exit();
},
```

**The replay**, from the run log:

| Time | Line | What happened |
|---|---|---|
| 22.553 | 33 | Click Sign in. The entry passes 57 ms later; the page is still the sign-in form |
| 22.621 | 29 | Second call. The title is not "Dashboard" yet, so no return (2 ms) |
| 22.626 | 30 | The `#cookie-reject` click waits while the page navigates to `dashboard.html`. The banner stays hidden there: the consent is already saved |
| 52.644 | 30 | The click times out after 30 s and heals. The model says "the cookie banner is already dismissed": ⚠ |
| 52.6–2:32 | 31 | The `#email` fill times out on the Dashboard. The model asks "should I navigate to the sign-in page?", which no one can answer: ✗ |

**Why it passes under AI.** After the click, the AI path waits for the URL
and the DOM to settle. Before judging line 29 it waits again, up to 10 s for
1 s of quiet. Each model turn adds seconds. The navigation always lands
first.

**Two defects:**

1. A compiled conditional return skips the wait that the AI path and
   compiled conditions both have (§2.3). The existing design meant to have
   it.
2. The click entry neither waits for what its click caused nor can fail:
   `dashboard || signInFormVisible` is true on the sign-in page. Generation's
   wait check (`unwaitedReadComplaint`, `generate.ts:744`) did not fire,
   because its list of instant reads (`generate.ts:688-689`) has no
   `title()` and no `isVisible()`.

### 3.2 Failure B: the read that reads too much

**Test:** `compile-loops.test.cjs`, "control-flow.md: the If, the While and
the Repeat compile to conditions, and the replay decides every one in code".
Failed in one of the two full runs. It has happened before: the test's own
comment records a measured run in which one compile in three read all three
spans of every row and stored nine values (`compile-loops.test.cjs:379-389`).
Generation is not deterministic, so this recurs.

**Step:** `Read the name of every account in the Your accounts panel [store
as: accounts]` (`templates/init/tests/control-flow.md`, line 50).

**The page** (`fixtures/test-app/control-flow.html:496-518`). Every row has
two spans without a `$`: the name, and the masked account number:

```html
<li class="account-row" data-testid="account-row" data-account="Everyday">
  <span>
    <span class="account-name">Everyday</span>
    <span class="account-number">•••• 4417</span>
  </span>
  <span class="account-balance" data-account="Everyday">$1,234.56</span>
</li>
```

**The AI run** read the first nested span of each row:

```
→ read[multiple] #account-list [data-testid="account-row"] > span > span:first-child text → accounts
read[multiple] captured: 3 values → variable "accounts"
```

**The compiled entry**, in full:

```ts
{
  source: 'Read the name of every account in the Your accounts panel [store as: accounts]',
  async run({ page, step, log }) {
    const accountRows = page.locator('#account-list [data-testid="account-row"]');
    const accountNames = page
      .locator('#account-list [data-testid="account-row"] > span > span')
      .filter({ hasNotText: '$' });
    await page.waitForFunction(() => {
      const rows = Array.from(
        document.querySelectorAll('#account-list [data-testid="account-row"]'),
      );
      return (
        rows.length > 0 &&
        rows.every((row) => {
          const name = Array.from(row.querySelectorAll(':scope > span > span')).find(
            (candidate) => !(candidate.textContent ?? '').includes('$'),
          );
          return (name?.textContent ?? '').trim().length > 0;
        })
      );
    });

    const accounts = (await accountNames.allTextContents()).map((name) => name.trim());
    const rowCount = await accountRows.count();
    step.setVar('accounts', JSON.stringify(accounts));
    step.expect(
      accounts.length === rowCount && accounts.every((name) => name.length > 0),
      'Read all populated account names from the Your accounts panel',
    );
  },
},
```

**On replay** the locator matched the name and the number in every row: 6
values for 3 rows. The `step.expect` failed 84 ms into the step, and the
step went red. The check did its job. Without it, `{{accounts}}` would have
held six values, account numbers included, and the For each after it would
have run six times.

**How the selector changed.** The entry was rewritten twice, and nothing
compared either rewrite with the recording:

- Generation's wait check fired on this entry although it takes no action, a
  false positive. The log shows its one re-ask:

  ```
  Code-behind re-asking for "Read the name of every account in the Your accounts panel
  [store as: accounts]": The entry reads a value out of the page and asserts on it
  without ever waiting for the state it asserts. …
  ```

- Review then rewrote the file (`Review — revised control-flow.steps.ts`).
  Its checklist says to prefer "stable selectors (ids, `data-testid`, roles,
  labels) over positional or index-based ones" (`review.ts:145-146`);
  generator rule 7 says the same (`src/ai/prompts.ts:2029`). Here
  `:first-child` is what picks the name over the number, and both rules
  invite dropping it. The log does not say which of the two rewrites did.
- No check compares the entry's selector with the one the AI read with.
  Review re-checks a revision for leaked values and broken condition entries
  (`review.ts:275`, `297-301`), but runs none of generation's four step-entry
  checks (`generate.ts:461-465`).

**Why it stayed red.** The self-check is a `step.expect`, so a wrong read is
a failed step, not a ⚠. Only entries that throw are marked stale
(`src/codebehind/last-run.ts`), and Run & Compile refuses to generate for a
step that did not pass (`live-compile.ts:554`). Nothing repairs it
automatically.

The generator wrote that check because its own rule tells it to: a capture
step must prove "the thing you read from was really there and really
populated" (`prompts.ts:2045`). The check was right to exist. What is wrong
is a wrong generated check failing the author's run (D4).

### 3.3 The post-action wait cannot see network work

`waitForPostActionSettle` compares the URL and a DOM fingerprint (body HTML
length, text length, element count) every 150 ms. It ignores the network on
purpose. Commit `808a3776` (2026-04-24) replaced a wait for `networkidle`,
which single-page apps with websockets, long-polls or analytics pings never
reach, so every action waited out its timeout. The request counter that
exists, `PageActivityTracker` (`page-state.ts:9`), counts every request on
the page and is used only to detect stalls (`step-executor.ts:2493-2496`).

Measured on 2026-10-07 by running the real `waitForPostActionSettle` against
a local page, one button per case (Appendix A):

| Click | Wait returned after | Saw a change | API still in flight | Page when the wait returned |
|---|---|---|---|---|
| Fast API (100 ms) | 878 ms | yes | 0 | loaded |
| Slow API (2 s), page unchanged until it answers | 1325 ms | no | 1 | the old page |
| Slow API (2 s), shows "Loading" first | 697 ms | yes | 1 | "Loading" |
| Fast API (100 ms) that fills an input | 1315 ms | no | 0 | value set, invisible to the fingerprint |

What that costs:

- **AI runs.** The next model turn sees the page captured at the end of the
  wait, so it can be shown the old page. It may click again, or ask a
  question no one can answer. Model think time and the prompt's rule to wait
  on loading indicators (`prompts.ts:783`) usually hide this.
- **Reports.** "DOM after action" can be the old page.
- **Compile.** The "page after the step" the generator is shown is captured
  right after the last wait (`step-executor.ts:3917-3924`). For a slow click
  the generator never sees what the click produced, so it cannot write the
  right check.

### 3.4 Related, and out of scope

  fixed that ("Don't pass a step on a bare action that never said it was
  done").
- **The SecureBank cookie step.** An unconditional "Reject non-essential

## 4. Goals and non-goals

**Goals:**

1. Failures A and B pass every time: `flow-control` 3 of 3, `compile-loops`
   5 of 5.
2. A compiled entry that acts on the page waits for what its action caused,
   slow requests included, within a bound.
3. A compiled read reads with the selector the AI run read with. A step
   that only reads is compiled from its recording, with no model, so its
   read is the run's read.
4. A wrong check the generator wrote costs a ⚠ and a repair, not a red run.
5. Replay stays fast, and every wait this spec adds is bounded and stated:
   up to about 1 s before a conditional flow-control line its values cannot
   decide (§6.1); at most 250 ms after an acting entry that starts no request
   (§6.4); about 300 ms before a compiled read once the page is stable
   (§6.6). A read-only entry never pays the network wait.
6. No new model calls on replay.
7. No change to the extension or the runner protocol in Phases 1–3 (D8).

**Non-goals, and what not to do:**

- **Do not wait for `networkidle`.** Commit `808a3776` removed it for good
  reason (`page-state.ts:195-200`, `265-267`).
- **Do not add replays or dry runs to Run & Compile**, and do not make the
  run wait for generation. Both contradict "Proof, not Replay".
- **Do not write one row's effects into an entry as required waits.** In
  `securebank-matrix.md`, "Click the Sign In button" navigates for row 1 and
  only shows an error banner for rows 2–5. Compile records row 1, so a
  compiled `waitForURL('**/dashboard.html')` would time out on four rows of
  five. The recording is also a local, git-ignored cache, so replay cannot
  rely on it.
- **Do not run entries against the recorded "page after".** It is
  truncated and attribute-filtered (`prompts.ts:1535`).
- **Do not heal assertions the author wrote**, or any check in an entry that
  acted: a heal after a click re-runs the step under AI and can submit
  twice.
- **Do not make `steptix compile`'s For-each pass-count check a failure**
  (`compile.ts:1095-1151`). A count cannot tell a wrong selector from a list
  that changed. (The `compile-loops` live test may assert its own count once
  §6.6 lands; that tests a fixed page, not the product check.)
- **Do not fix this with prompt wording alone.** B's prompt already showed
  the right selector and the values it read.
- **Do not change the hot-path system prompt.** Every prompt change here is
  in the generation, repair and Review prompts.

## 5. Decisions

- **D1.** A compiled conditional flow-control line (`If … then return`,
  `then stop`, `then fail`) waits for the page exactly as the AI judgement
  does. This extends `stories/step-flow-control.md` decision 6 to code, as
  `settleBeforeConditions` already did for compiled conditions. It stays
  after §6.4 lands: §6.1 waits before a judgement, §6.4 after an acting
  entry.
- **D2.** After a compiled entry that acts, the runtime waits for the
  first-party requests that began while it ran, then for the page to be
  quiet, within a bound. It never waits for the network as a whole. The
  watcher cannot tell which code started a request, so "began while it ran"
  is the rule, not "started by the entry".
- **D3.** A compiled read keeps the selector the AI run read with. This is
  checked after generation, after Review and after repair. A step whose code
  still reads with a different selector after one re-ask gets no entry: it
  runs on AI and the next compile tries again. The check yields to the
  selector story's carve-out: where a positional target is distinguished by
  a parameter, the entry builds a data-driven locator instead
  (`stories/codebehind-selector-ambiguity.md:296-302`).
- **D4 (approved 2026-10-07).** A failed check that the generator wrote, in
  an entry that takes no action, heals like broken code. Assertions the
  author wrote, and checks in entries that acted, still fail. This amends
  `stories/step-codebehind.md:274-280`.
- **D5.** What a run observed about an action (its navigation, its requests)
  is evidence shown to the generator. It is never a requirement written into
  the code.
- **D6 (approved 2026-10-07).** §6.1 ships first as a stopgap. §6.4 is the
  fix for the class, because §6.1 waits for 1 s of quiet, and an API slower
  than that still races.
- **D7 (approved 2026-10-07).** A step that only reads or counts is
  compiled from its recording, with no model. Its entry runs the same read
  code the AI's action ran, so it reads what the run read. This extends
  `docs/specs/SPEC-structured-table-reads.md` §9.2, one extractor shared by
  the AI action and generated code, from table reads to plain reads and
  counts. §9.2 keeps its own `tables.read` shape, which returns rows for the
  entry to store; `step.read` returns values and also stores them when given
  `as`.
- **D8.** Phases 1–3 report through what already exists. A step left without
  code is counted in Run & Compile's existing "could not be generated; they
  stay AI" line, and listed by the CLI compile the way a condition without an
  entry is. A failed `step.check` is an ordinary stale entry, with the
  existing ⚠ hover. So nothing under `steptix-vscode/` or `runner-core/`
  changes, and no version bump is needed. An item that finds it must change
  either says why and bumps the version (§7).

### 6.1 Wait before a compiled conditional flow-control line

**Fixes:** failure A, for logins that answer within about 1 s.

**Design:**

- In `executeStep`, before `runCodeBehindStep` (`step-executor.ts:854-855`):
  when the step claims conditional flow control
  (`opts.flowControlClaim?.body !== undefined`, which covers `If … then
  return`, `then stop` and `then fail`) and the run's values do not already
  decide it (`decideConditionLocally`, as used at `step-executor.ts:1110`),
  call `await settleBeforeConditions(opts, { followNavigation: true })
  .catch(() => {})`. That is the AI judgement's own wait: up to 10 s, 1 s of
  quiet.
- Give `waitForPageStability` (`page-state.ts:310`) a `followNavigation`
  option, off by default. Today, when a navigation destroys its quiet-wait
  script, the catch returns at once (`page-state.ts:367-371`), which ends
  the wait at the very moment A needs it to continue. With the option on:
  - the page **navigated** if `page.url()` changed since the wait began, or
    the error says the execution context was destroyed;
  - if it navigated and the page is not closed, wait for `domcontentloaded`
    within the remaining budget, then run the quiet wait once more with
    what is left;
  - at most one such re-wait; any other rejection returns at once, as today;
  - `now` is injected, for tests.
- Who passes `followNavigation`: the new call above, and compiled condition
  entries (`control-runtime.ts:882`, through `settleBeforeConditions`), which
  have the same race. The model's condition judge (`step-executor.ts:4443`)
  and the AI flow-control gate (`step-executor.ts:2428`) share the same
  function and keep today's behaviour, so AI timing does not change. They
  have the same race in principle (§9).

Without `followNavigation`, the first change does not fix A: the login
answers inside the 1 s window, the navigation kills the wait, and the title
is read mid-load.

**Limit:** a login slower than 1 s still races, because the page is quiet
while the request runs. §6.4 closes that.

**Files:** `step-executor.ts`, `page-state.ts`, `control-runtime.ts`.

**Unit tests:**

- In `tests/codebehind-flow-control.test.ts`, which has the code-behind
  binding harness (`:93-101`, `:275-320`), mock page-state the way
  `tests/flow-control-executor.test.ts` does (`:66-88`). Then: a claimed
  entry runs as settle, then entry, with
  `{ timeoutMs: 10_000, quiesceMs: 1000, followNavigation: true }`; an
  unclaimed entry does not settle; a line its values decide does not settle.
- That file's fakes reject every `evaluate` (`:229`). With an unchanged URL
  and a generic error, the wait must return at once, as today; keep a test
  for that.

### 6.2 A compiled read keeps the recorded selector

**Fixes:** failure B. Once §6.6 lands, a step that only reads, like B's, is
compiled from its recording and never reaches this check; the check then
guards the reads in steps that also act.

**Design:**

- **The check.** A new check in `staticEntryComplaint` (`generate.ts:537`).
  For every recorded `read` or `count`, the entry must contain that
  action's selector as a string: as recorded, after parameter substitution,
  or as `targeting.resolvedSelector`. Compare after normalising whitespace
  and quote style. Otherwise re-ask once, with a complaint like:

  > The recorded run read with
  > `#account-list [data-testid="account-row"] > span > span:first-child`,
  > which matched 3 elements and captured 3 values. Your entry reads with a
  > different selector. A read that matches more or fewer elements does not
  > throw; it returns different data. Use the recorded selector as written.

  Reads are the one action where a wrong selector fails silently, which is
  why they get their own check.
- **Exemptions.** A selector containing a `{{placeholder}}`, which the entry
  builds from `step.getVar`. And the selector story's carve-out: a recorded
  read whose `targeting.resolvedBy` is `positional` while the step text or a
  parameter names what distinguishes the element. There the entry must build
  a data-driven locator from `step.getVar`
  (`stories/codebehind-selector-ambiguity.md:296-302`), and this check does
  not apply.
- **Which answer wins** after the one re-ask:

  | First answer | Re-ask | Kept |
  |---|---|---|
  | Passes every check | (not asked) | first |
  | Fails the read check | Fixes it, passes the rest | re-ask |
  | Fails the read check | Fixes it, fails another check | re-ask, with today's warning for the other check |
  | Fails the read check | Still fails it | **neither: the step gets no entry** |
  | Fails another check only | Fixes it, keeps the read | re-ask |
  | Fails another check only | Breaks the read | first, with today's warning for the other check |

  Today the second answer is always taken (`generate.ts:486-527`).
- **No entry, when the read still differs.** Compile writes nothing for the
  step, exactly as if it had never been compiled:
  - the next run uses AI for the step, which reads what the recorded run
    read;
  - the next Run & Compile tries the step again, because a step with no
    entry is in its default selection.

  How each compile path does it:
  - **Run & Compile**: return a generation `error` with the reason. That path
    already leaves the step on AI with no entry, notes why, and counts it in
    "N step(s) could not be generated; they stay AI"
    (`live-compile.ts:1732-1745`, `1946`). The note names the step and says
    "its code did not read with the selector the run used".
  - **CLI `steptix compile`**: an `error` there fails the whole compile
    (`compile.ts:981-994`), so add a `stepsNotCompiled` list modelled on
    `conditionsNotCompiled` (`compile.ts:812`, `997-1003`): the step leaves
    the replay selection and is listed in the output.

  This departs on purpose from generation's rule that a textual check must
  never fail a compile (`generate.ts:486-492`): it fails nothing, it leaves
  one step on AI. The alternatives are worse. Keeping the wrong code replays
  a wrong read, which §6.5 can only turn into a fallback to AI on every run,
  and only if its self-check notices. Writing `ai: true` keeps the step on AI
  for good, because compile never regenerates the author's opt-out.
- **Repair answers get the same check.** Pass `actionsOf(result)` into the
  repair input (`RepairPromptInput`, built at `live-compile.ts:1635-1658`;
  `compile.ts:929`) and run generation's static checks, this one included, on
  repair answers, with the same precedence and the same no-entry outcome.
  Today repair answers get only the leak guard. Under §6.5 this is the path a
  wrong read regenerates through.
- **Review's output gets the same check.** After a revision passes today's
  rejections (`review.ts:270-306`), run generation's static checks on every
  entry the revision changed. If a changed entry newly fails one, reject the
  revision for that file, as the other rejections do: "rejected: the
  revision changes the selector step 50 read with — the generated file
  stands". Pair entries before and after the way `conditionEntryBroken`
  does (`review.ts:297-301`, `326-354`). Review needs, per entry, the
  recorded actions and the substitution values of the pass that generated
  it. For an entry used more than once (a section called twice, a loop
  body), that is the first pass to reach it, the one whose transcript it was
  generated from (`live-compile.ts`, `takenKeys`).
- **A log line** whenever Review changes a selector string in an entry, so
  the log answers the question §3.2 could not.
- **Wording**, which supports the check but does not replace it. Four places
  tell the model to swap selectors for stable handles: Review's item 5
  (`review.ts:145-146`), generator rule 7 (`prompts.ts:2029`),
  `SELECTOR_RULE_INFERRED` (`prompts.ts:1519-1520`) and the "unmeasured"
  bullet (`prompts.ts:1582-1584`). Each gains: a selector the recording read
  with is part of what was read, and is kept as written, `:first-child`
  included. Prefer stable selectors only when writing a new one.

**What the check can and cannot tell.** "Right" here means "reads what the
recorded run read". The run is the only reference compile has: the AI read
the page, the step passed, and the runtime recorded the selector, how many
elements it matched and how many values it captured. Nothing runs the
generated code before Apply (§2.1), so the check cannot test the code. It
compares the code with the recording:

- **The same selector** on the same page reads the same elements. The check
  passes.
- **A different selector** may or may not be equivalent, and the check
  cannot tell, so it treats it as wrong. `#account-list .account-name` would
  have read the same three names here, and is refused anyway. The cost is a
  re-ask, and at worst a step left on AI until a later compile.
- **The same selector, narrowed afterwards** (`.first()`, `.filter(...)`)
  passes the check and can still read something different. The backstop is
  the self-check on replay (§6.5).
- **Whether the run's own selector was a good one** is not judged. If the
  page changes later, the replay's self-check catches it, and the step falls
  back to AI and is recompiled.

**Files:** `generate.ts` (the check, the precedence, the no-entry outcome);
`review.ts` (the check on revisions, item 5, the log line); `live-compile.ts`
and `compile.ts` (recorded actions to Review and repair; `stepsNotCompiled`);
`repair.ts` (its input); `prompts.ts` (the selector wording).

**Unit tests:**

- The check: B's exact strings give a complaint; the recorded selector kept
  gives none; a selector built from `step.getVar` that matches the
  substituted recording gives none; a placeholder selector and the
  positional carve-out are exempt.
- Precedence, with a scripted fake AI client: one test per row of the table.
- No entry: in Run & Compile the step is counted as not generated and the
  note names the reason; in the CLI compile the step leaves the replay
  selection, is listed, and the compile does not fail.
- Repair: a repair answer that reads with a different selector is re-asked,
  and withheld if it still differs.
- Review: given a revision that drops `:first-child`, `reviewCandidate`
  rejects it and leaves the candidate unchanged (alongside the existing
  `reviewCandidate` tests in `tests/codebehind-compile.test.ts`); an entry
  used twice is checked against its first pass.

**Live check:** `compile-loops.test.cjs` ×5: the proposed read entry
contains the selector printed in that run's `→ read[multiple]` log line (the
AI may choose a different selector from B's on another run), and the run
prints no `[live] WARNING` about the For-each passes. The test only warns
about that count today (`compile-loops.test.cjs:390-398`); see §8.
`compile-codebehind.test.cjs` ×1.

**Risks:** a false positive when the model writes a selector that would
have read the same elements, such as a chained locator or `.account-name`;
that costs one re-ask, and at worst leaves the step on AI until a later
compile. Rejecting a Review revision also discards any good edits it made to
the same file.

### 6.3 Sharpen the unwaited-read check, and define "acting"

**Fixes:** catches A's click entry at compile time, and stops the false
re-ask that started B's rewrite.

**Design:**

- **Add the reads it misses** to `INSTANT_READ` (`generate.ts:688-689`):
  `title()`, `url()`, `isVisible()`, `isHidden()`, `isEnabled()`,
  `isChecked()`, `isEditable()`, `count()`, `innerHTML()`.
- **`entryActs(code)`**, in a new shared module,
  `src/codebehind/entry-actions.ts`, because the runtime imports it too
  (§6.4, §6.5). It answers true when the entry's code calls any of:
  - page and locator actions: `click`, `dblclick`, `tap`, `hover`, `fill`,
    `clear`, `press`, `pressSequentially`, `type`, `check`, `uncheck`,
    `setChecked`, `selectOption`, `setInputFiles`, `dragTo`,
    `dispatchEvent`, `focus`;

  - `keyboard.*`, `mouse.*`, `touchscreen.*`;

  - `page.request.*` and `context.request.*`;
  - `evaluate`, `evaluateHandle`, `addScriptTag`, which can change the
    page;
  - **any function the entry or its file defines itself**: a helper may do
    any of the above, so an unknown call counts as acting. This is the
    fail-safe that keeps §6.5 from healing a step that clicked.
- **Fire only after an action.** The check fires when a call that
  `entryActs` counts comes before the read. A read-only entry, like B's, has
  nothing to wait for.
- **Count `step.check(`** as an assertion alongside `step.expect(`, once
  §6.5 lands.
- **The complaint** gains a navigation example: wait for the page the action
  leads to, with `await step.settle()` once §6.4 lands, and until then with
  `page.waitForFunction(() => document.title.includes('Dashboard'))`. Never
  with a URL taken from one data row.
- **Not in scope:** flagging hedged checks such as `step.expect(a || b)`.

**Existing tests that change:** `tests/codebehind-generate.test.ts:742-751`

### 6.4 A network-aware wait after acting entries, and `step.settle()`

**Fixes:** A's whole class, slow logins included. Also an AI step that
follows a compiled step and captures its first page mid-navigation
(`step-executor.ts:2455-2465`), and, through `step.settle()`, an entry's own
check racing its own click.

**Design.** A watcher, armed on the browser context just before an entry's
`run`, so that requests from a new tab count too.

- **What it tracks.** A request that begins after arming, whose type is
  `document`, `fetch` or `xhr`, and which is first-party: same origin as the
  active page when armed. A main-frame document request always counts.
- **What it ignores.** WebSockets, EventSource, beacons and pings, images,
  fonts, scripts, third-party hosts, and anything already open when it was
  armed, such as a long-poll.
- **Attribution.** The watcher cannot tell which code started a request, so
  any first-party request that begins while it is armed counts (D2). A poll
  or heartbeat that starts in the window is waited for, up to the budget.
- **When it waits.** After `run` returns, when
  `entryActs(entrySourceText(entry))` is true (`execute.ts:661`). Read-only
  entries skip it. It also runs when an acting entry throws, before the step
  falls back to AI, so the healing model sees the page the entry left rather
  than one mid-request.
  1. While any tracked request is pending, wait. Requests that begin
     meanwhile, such as the navigation after a login, join.
  2. Then wait for the URL and the DOM fingerprint to be unchanged for
     600 ms.
  3. Quick exit: if nothing was tracked and nothing changed, stop after
     250 ms.
  4. Budget: `min(10 s, execution.timeout)`, the same as the flow-control
     wait. At the budget, log what is still pending ("the wait after step 33
     stopped at 10 s; still pending: POST /api/slow") and carry on. It is
     never a failure.
  5. No page, the computer surface, or no DOM signal when armed: skip.
     `capturePageSignal` returns a new synthetic fingerprint on every failed
     read (`page-state.ts:235-239`), which would otherwise spin to the
     budget.
- **Where.** In `runCodeBehindStep`, before the step's screenshot
  (`step-executor.ts:1383-1390`), so the report shows the result.
- **API**, exported from `page-state.ts` so Appendix A and §6.9 can use it:

  ```ts
  armActionWatcher(context: BrowserContext, page: Page, opts: {
    budgetMs: number; quietMs: number; quickExitMs: number;
    now?: () => number; sleep?: (ms: number) => Promise<void>;
  }): { settle(signal?: AbortSignal): Promise<SettleReport>; dispose(): void }

  type SettleReport = { waitedMs: number; tracked: number; stillPending: string[] };
  ```

  Inside, a pure state machine fed events (request began, request finished,
  signal sampled), so the unit tests need no real timers.
- **`step.settle()`.** The same wait, callable inside an entry: click, then
  `await step.settle()`, then read. It waits on the watcher armed for this
  entry. It names no URL, so it holds for data rows that navigate and rows
  that do not. `WAITS_FOR_STATE` (`generate.ts:700-717`) accepts it. It needs
  the page or page tracker, the browser context, the budget from config and
  the abort signal inside `makeStepApi` (`execute.ts:528`);
  `RunCodeBehindOptions` carries none of these today, so they are added.
- **Prompts.** Generator rule 5 and the post-condition rule
  (`prompts.ts:2027`, `2039-2045`), the repair prompt's post-condition rule
  (`src/codebehind/repair.ts:86`) and Review's item 3 (`review.ts:140-142`):
  after an action that changes the page, `await step.settle()` before
  reading or asserting, then wait for the named state when the step states
  one.

**What A looks like with it:** line 33's click starts `POST /api/login`,
which is tracked. When it answers, the document request for `dashboard.html`
begins and is tracked too. The page loads, stays quiet for 600 ms, and only
then does line 29 read the title: "Dashboard", so it returns.

**Files:** `page-state.ts` (the watcher); `step-executor.ts`
(`runCodeBehindStep`); `execute.ts` and `types.ts` (`step.settle()`, the
plumbing); `prompts.ts`, `repair.ts`, `review.ts`; `generate.ts`
(`WAITS_FOR_STATE`).

**Unit tests:** for the watcher, on a fake clock:

- a request open at arming is ignored;
- a third-party request is ignored;
- a chained request is tracked;
- a poll that begins in the window is waited for, up to the budget;
- at the budget it logs and does not fail;
- the quick exit;
- the skip with no DOM signal.

For the executor, with page-state mocked: it waits after a passing acting
entry, before the screenshot; it waits after an acting entry that threw,
before the heal; it does not wait after a read-only entry. For the step API:
`step.settle()` waits on the entry's watcher.

**Live check:** the full suite ×2; `flow-control` ×3; `compile-loops` ×3;
the slow-login variant (§8). Acceptance: no compiled replay gets more than
20 % slower, and the full suite's wall time grows by no more than 5 %. Report
each file's replay wall time before and after in the PR.

**Risks:** replays get slower, by at most 250 ms for an acting entry that
starts no request, and otherwise by the time its requests actually take. A
click that starts first-party polling pays the budget every time; the log
names the request.

> **As built (2026-10-08).** Measured live, the design as written cost a
> compiled click about 0.9 s (median 61 ms → 974 ms over 41 steps; compiled
> replays 59–239 % slower): 600 ms of quiet after any change to the page,
> then a second quick-exit window after an entry that had already settled
> itself. Two changes keep the waits for network work as designed and bring
> the rest within the bound above. With no request tracked, a settle ends
> once the page has held still for `quickExitMs` (250 ms), not `quietMs`.
> And the runner's wait after an entry whose code ends with `step.settle()`
> after its last action (`settlesAfterLastAction`) returns at once unless a
> request began or the page changed since (`settle(signal, { ifActive: true
> })`).
>
> Re-measured against `ba80b365` with those changes: compiled steps that act
> went from a median 73 ms to about 385 ms, and compiled replays of the
> fixture tests were 28–169 % slower. The runner's own wait after an entry is
> now a median 2 ms; what remains is the 250 ms quick-exit window inside each
> entry's own `step.settle()`. On the local fixture app, where an acting step
> took 60–70 ms, the 20 % acceptance above cannot be met with that window.
> The project owner kept 250 ms (§9 Q2) on 2026-10-08: robustness over
> replay speed, at about 0.3 s per compiled step that acts.

### 6.5 `step.check`: a failed self-check in a read-only entry heals

**Fixes:** B's outcome. A wrong generated read becomes a ⚠ and a repair,
not a red run, and the repair gap in §3.2 closes.

**Design:**

- **A new `step.check(condition, message)`.** It fails with
  `CodeBehindCheckError`, which is not a `CodeBehindExpectationError`, so the
  runner treats it as broken code (`step-executor.ts:1364`): the step heals
  under AI, the entry is marked stale, and repair picks it up. The error
  message starts "Self-check failed: ", followed by the check's message.
- **Only in entries that take no action.** When the entry loads,
  `entryActs(entrySourceText(entry))` decides. In an acting entry,
  `step.check` fails like `step.expect`, because a heal after a click re-runs
  the step and can submit twice. Because `entryActs` counts any helper call
  as acting, an entry that clicks inside a helper cannot heal this way.
- **In a `condition` entry**, `step.check` is a throw like any other: the
  entry is marked ⚠ and the model decides for the rest of the run, as
  today.
- **`step.expect` is unchanged.** An assertion the step states fails the run.
  Mechanically, a step states an expectation when its recorded transcript
  contains an `assert` action.
- **The generator** is offered `step.check` only when the step's recorded
  actions are all reads, counts, finds or expands, with no `assert`: capture
  and read steps like B's, for the check its post-condition rule asks for
  (`prompts.ts:2045`). Review's item 3 says the same. A static check rejects
  `step.check` in an entry that acts.
- **Strict replay and keyless runs** still never heal, as today.
- **§6.6's `step.read` and `step.count`** fail their own self-check the same
  way, so a read compiled from the recording that stops matching falls back
  to AI too.
- **What the author sees** is unchanged in kind: an ordinary stale entry, and
  the extension's existing ⚠ hover, "This step passed under AI — its
  compiled code-behind threw" (`steptix-vscode/src/extension/failure-hover-core.ts:79-84`),
  with the "Self-check failed: …" message quoted under it. So nothing in the
  extension or the runner protocol changes (D8).
- **The story** gets an amendment in the repo's style, a blockquote after
  `stories/step-codebehind.md:280` like the one at `:267`: "> **Amended by
  [SPEC-codebehind-robustness.md](../docs/specs/SPEC-codebehind-robustness.md)
  §6.5.** A failed self-check in an entry that takes no action is broken
  code: it heals."

**What B looks like with it:** the entry reads 6 values and `step.check`
fails. The step re-runs under AI and reads 3. The step shows ⚠ with
"Self-check failed: one name per account row (6 names for 3 rows)", and the
run carries on. The next compile regenerates the entry: it is in the default
selection, in Compile This Step, and in `--only-stale`.

**Files:** `execute.ts`, `types.ts`, `step-executor.ts`, `prompts.ts`,
`review.ts`, `generate.ts`, `stories/step-codebehind.md`.

**Unit tests:** heals on a normal run; red under strict replay;
`codeBehindHealSkipped` on a keyless run; `step.check` in an entry that
clicks, or calls a helper, fails without healing; a `condition` entry's
`step.check` behaves like any throw; `step.expect` unchanged.

**Live check:** `compile-loops` ×3; `verify-assertions` ×1 and
`failure-outcomes` ×1, where assertions must still fail.

**Risks:** it changes a recorded rule (approved, D4). A heal costs an AI
call on that run.

### 6.6 Steps that only read are compiled from the recording

**Fixes:** B's class, for every step that only reads or counts. The
compiled read is the run's read by construction, so the mistake in B cannot
happen. It also removes the model call, and its cost, for those steps.

**The idea.** When the AI performed B's step, it did not write code. It
chose a `read` action, and Steptix carried it out. The recording keeps that
action exactly:

```json
{ "action": "read", "multiple": true, "as": "accounts",
  "selector": "#account-list [data-testid=\"account-row\"] > span > span:first-child" }
```

Everything after that was Steptix's own code. `executeAction` cleaned the
selector and resolved its frame (`src/browser/actions.ts:317-351`), and
`executeReadMultiple` (`actions.ts:2195`) read each match: an input's
`value`, otherwise its trimmed text; `href` and `src` resolved when an
attribute was asked for; `pattern` applied to each value; at most 500
values. The result was stored as a JSON list (`step-executor.ts:3580-3591`).
The model chose only the selector.

So for a step like this, compile writes the entry from the recording,
without asking a model:

```ts
{
  source: 'Read the name of every account in the Your accounts panel [store as: accounts]',
  fromRecording: true,
  async run({ step }) {
    await step.read({
      selector: '#account-list [data-testid="account-row"] > span > span:first-child',
      multiple: true,
      as: 'accounts',
      kinds: ['span.account-name'],
    });
  },
},
```

`step.read` takes the same path the AI's read took and stores the result the
same way. Same selector, same reading rules, same storage: on the same page
it produces exactly what the run produced. A single read with a pattern, and
a count, have the same shape:

```ts
await step.read({ selector: '#balance', pattern: '\\$([\\d,.]+)', as: 'balance', kinds: ['span.balance'] });
await step.count({ selector: '#documents-body > tr.doc-row', as: 'document_count', kinds: ['tr.doc-row'] });
```

The project has made this decision once already, for table reads:
generated code must call the same table reader as the AI action. "There
must not be one header algorithm in generated code and another in
`actions.ts`" (`docs/specs/SPEC-structured-table-reads.md` §9.2). That
helper is not built yet, so table-read steps stay on AI for now
(`generate.ts:56-70`). This applies the same rule to plain reads and counts,
and goes one step further: a step that only reads needs no model at all.

**Which steps qualify.** All of these must hold:

- Every recorded action is a `read` or a `count`. `find` and `expand` are
  ignored: they only showed the model the page. So is `noop`, which did
  nothing; it is how the model keeps a list read it was shown (below).
- Every variable the step captured came straight from one of those actions,
  so the entry stores exactly what the run stored.
- The step states no expectation: the transcript has no `assert` action.
- The step ran on the browser surface.
- No recorded selector contains a resolved parameter value. A model that
  wrote row 1's value into a selector, instead of `{{account}}`, would
  freeze row 1. The leak guard that already refuses parameter values in
  generated code (`generate.ts:884-892`) decides, and such a step goes to
  the model with its placeholder rule.
- No recorded read falls under the selector story's positional carve-out
  (§6.2); those go to the model, which builds the locator from the
  parameter.

Every other step goes to the model as today. For a step that also acts (a
click, then a read), the generation prompt tells the model to do the read
with `step.read(…)` and the recorded action's fields rather than writing its
own. §6.2 checks the selector either way.

**Design:**

- **`step.read(options)` and `step.count(options)`** on the step API
  (`execute.ts`, `types.ts`). The options are the recorded action's fields:
  `selector`, `multiple`, `attribute`, `pattern`, `frame` and `as`, plus
  `kinds` (below). `step.read` returns the value, or the list for
  `multiple`; `step.count` returns a number. Each stores its result too when
  given `as`.
- **The same path, not just the same function.** Both go through
  `executeAction` with a `read` or `count` action built from the options,
  not straight to `executeReadMultiple`. `executeAction` cleans the selector,
  moves an iframe written into it to the frame field, and resolves the frame
  first (`actions.ts:317-351`), and the recording keeps the action as the
  model emitted it, before any of that (`step-executor.ts:3641`).
- **Names.** The recorded `as`, and any `{{placeholder}}` in the recorded
  fields, use the run's names, which inside a skill body or a looped section
  are renamed. Map them back to the authored names through
  `binding.scope.renames`, as `recordedCapturesOf` does
  (`generate.ts:255-268`), and store through `step.setVar`'s path
  (`execute.ts:597-608`), so the frame's scoping applies. Placeholders are
  filled at replay with the substitution the AI path uses.
- **One way to store a capture.** The code that stores a capture on the AI
  path (`step-executor.ts:3565-3614`) moves into a helper both paths call,
  masking of secret values included.
- **Plumbing.** `makeStepApi` (`execute.ts:528`) needs the page or page
  tracker, the measure options, the step timeout, the run's secrets for
  masking, and the abort signal. This extends what §6.4 adds.
- **Waiting.** The AI's read ran on a page that had already settled, after
  the model's think time. A count and a multiple read do not wait for
  elements (`actions.ts:2026`, `2209`): they return whatever matches at that
  instant. So `step.read` and `step.count` first wait until the number of
  matches has stopped changing for 300 ms, within the step's timeout. A
  single read already waits for its first match.
- **A self-check: the elements read are the kind the run read.** During
  compile runs, each read and count records the kinds of element it matched:
  the tag name plus class names, leaving out generated-looking ones
  (anything containing a digit). For B's read that is `span.account-name`.
  This is a new `kinds` field on `ActionTargeting` (`actions.ts:105`),
  collected in the read and count cases (`actions.ts:510-564`) only when
  `targeting` is, and shown in `targetingLegend` (`prompts.ts:1532`) so the
  model path sees it too. The entry carries the kinds as `kinds`. On replay,
  if any matched element is of another kind, the read fails its self-check
  as §6.5 defines it: the entry takes no action, so the step falls back to
  AI and the entry is regenerated. This is the check that would have caught
  B: its selector matched both `span.account-name` and `span.account-number`.
  An empty result passes.
- **Only a read the AI run stood by is compiled** (steptix/steptix#48, which
  #28 was merged into). Under AI, a read of every match or a count that comes
  back empty, or matches more than one kind of element, is shown to the model
  before the step can end on it: what the selector matched, kind by kind, with
  a few values of each (`src/runner/list-read-review.ts`). The model reads
  again, and the new read replaces the old, or it keeps the read. A changed
  read is shown again while the step has turns left; with none left (the last
  turn, or a `return`), the step ends on the read as it came back, unseen,
  and passes. `actionsOf` drops every reviewed read a later action stored
  over, in any attempt, so a read the model replaced — B's over-broad
  selector, or one that matched nothing — never reaches the entry.
- **A read that proves nothing is not compiled at all.** A step that ended on
  a list that came back empty, kept or not, or on a list the model never saw,
  is no evidence for its selector: on a page with no items, a selector one
  level too deep matches nothing just as the right one does, and the entry
  would pass on that page for good (`unprovenListRead`). Both compilers treat
  it as they treat a tolerated failure: not attempted, named with the reason,
  no entry — never `ai: true` — so the next compile takes it again. A loop
  body takes its evidence from the first pass whose reads did prove something
  (`isEvidencePass`), so a `For each` that read nothing on its first item and
  three values on its second compiles from the second.
- **Review leaves these entries alone.** They carry `fromRecording: true`.
  Review's prompt says not to change them, and a revision that changes one is
  rejected, as the other rejections are (`review.ts:270-306`). The rejection
  keys on the entry *before* the revision, because a revision can delete the
  flag.
- **Each compile path:**
  - **Run & Compile generation:** a branch before the model is asked
    (`askModel`, `live-compile.ts:1551`).
  - **Run & Compile repair** of a stale `fromRecording` entry
    (`askForRepair`): write it again from this run's transcript, the AI pass
    that healed it, with no model. The AI chose a fresh selector on that
    pass, so a change to the page repairs itself. This uses the live run's
    transcript, which is consistent with the selector story's decision not
    to repair from the on-disk recording
    (`stories/codebehind-selector-ambiguity.md:615-617`).
  - **CLI `steptix compile` generation:** the same branch.
  - **CLI strict replay rounds:** a failing `fromRecording` entry has no new
    transcript in that round, because strict replay does not heal. Give it no
    entry (`stepsNotCompiled`, §6.2) rather than `ai: true`, so the next Run &
    Compile writes it again from a live run.
- **Table reads** keep §9.2's own `tables.read` shape. Add an "> **Extended
  by**" note to `SPEC-structured-table-reads.md` §9.2 pointing here.

**What it gives up.** The selector is frozen, as in any compiled entry:
under AI, the model picks a selector afresh on every run. The kinds check and
§6.5 make a later change to the page cost a ⚠ and a recompile, not wrong
data.

### 6.7 Show the generator which actions navigated

The runtime already records, per action, the URL the action ran on
(`actionPageUrl`, `step-executor.ts:3661`). `actionsOf`
(`src/codebehind/recording.ts:794-806`) drops it before the prompt.

- `actionsOf` carries `navigated: { from, to }` when an action's
  `actionPageUrl` differs from its `pageUrl`. Merge it inside `actionsOf`,
  before redaction, as `recording.ts:769-774` requires: a URL can carry a
  secret.
- The prompt gains one legend line, only when an action navigated, so every
  other prompt stays byte-identical: "An action with `navigated` changed the
  page's URL on this run. The entry must wait for the page it leads to
  before anything after it, with `await step.settle()`, and must not
  hard-code the URL: other rows of a data table may not navigate." Until
  §6.4 lands, it names `waitForFunction` instead.
- A static check in §6.3's family: an action navigated on this run, and the
  entry has no wait after its last action.

**Limit:** `pageUrl` is captured after the post-action wait, which gives up
at 3.5 s (`step-executor.ts:3546-3552`, `3633`), so a navigation slower than
that is missed until §6.9 lands.

**Unit tests:** `actionsOf` with and without `actionPageUrl`; the legend line
present only when something navigated; the check fires on A's line 33 entry.

### 6.9 The same wait on AI steps during compile runs

- During compile runs only (`captureStepContext`), after each acting AI
  action, run §6.4's watcher after `waitForPostActionSettle`, not instead of
  it. Ordinary runs keep today's wait.
- The "page after the step" then shows what slow requests produced, so the
  generator sees the result it must check for.
- Each sub-action records the requests that began in its window,

  "observed on this run", with a legend line only when some action has
  requests: evidence, never a requirement (D5).

  drop the request list.

## Appendix A. The settle probe

The measurement in §3.3. Save it outside the repo and run it with the repo
root as its argument, after `npm run build`:
`node settle-probe.mjs C:/path/to/steptix`. The final
`waitForLoadState('networkidle')` in each case only lets slow requests drain
before the next case; it is not part of the measurement.

```js
import http from 'node:http';
import { createRequire } from 'node:module';
import { pathToFileURL } from 'node:url';

const repo = process.argv[2];
const require = createRequire(`${repo}/package.json`);
const { chromium } = require('playwright');
const { waitForPostActionSettle, capturePageSignal } = await import(
  pathToFileURL(`${repo}/dist/browser/page-state.js`).href
);

const html = `<!doctype html><html><body>
<button id="fast">Fast</button><button id="silent">Slow, quiet</button>
<button id="spinner">Slow, spinner</button><button id="value">Fills an input</button>
<div id="out">idle</div><input id="field">
<script>
  const out = document.getElementById('out');
  const field = document.getElementById('field');
  const load = async (ms) => (await fetch('/api?ms=' + ms)).text();
  fast.onclick = async () => { out.textContent = await load(100); };
  silent.onclick = async () => { out.textContent = await load(2000); };
  spinner.onclick = async () => { out.textContent = 'Loading'; out.textContent = await load(2000); };
  value.onclick = async () => { field.value = await load(100); };
</script></body></html>`;

const server = http.createServer((req, res) => {
  const url = new URL(req.url, 'http://x');
  if (url.pathname === '/api') {
    const ms = Number(url.searchParams.get('ms'));
    setTimeout(() => res.end(`Loaded after ${ms} ms`), ms);
    return;
  }
  res.setHeader('content-type', 'text/html');
  res.end(html);
});
await new Promise((r) => server.listen(0, '127.0.0.1', r));
const base = `http://127.0.0.1:${server.address().port}/`;

const browser = await chromium.launch();
const page = await browser.newPage();
const inflight = new Set();
page.on('request', (r) => { if (r.url().includes('/api')) inflight.add(r); });
page.on('requestfinished', (r) => inflight.delete(r));
page.on('requestfailed', (r) => inflight.delete(r));

const rows = [];
for (const id of ['fast', 'silent', 'spinner', 'value']) {
  await page.goto(base);
  inflight.clear();
  const preSignal = await capturePageSignal(page);
  const t0 = Date.now();
  await page.click(`#${id}`);
  await waitForPostActionSettle(page, { preSignal });
  const post = await capturePageSignal(page);
  rows.push({
    button: id,
    returnedAfterMs: Date.now() - t0,
    sawChange: post.domFingerprint !== preSignal.domFingerprint,
    apiInFlight: inflight.size,
    out: await page.textContent('#out'),
    field: await page.inputValue('#field'),
  });
  await page.waitForLoadState('networkidle');
}
console.table(rows);
await browser.close();
server.close();
```
